# 自动目验（UI_AUTO_VERIFY）· 选型分析与实现

> 目的：把「待用户目验」转为「CI 自动验证」，解除验收瓶颈。
> 依据：`docs/SELF_DIAGNOSIS_REPORT.md`（瓶颈判断：**验证速度**，非方案质量）
> 本目录是**测试工具**（devDependency）；**产物仍保持零第三方依赖**（ADR-002 红线未破）。

---

## 1. 无头浏览器选型（系统自判）

### 1.1 候选对比

| 方案 | 依赖 | 能否执行 wasm | 稳定性 | CI 支持 | 结论 |
|---|---|---|---|---|---|
| **Playwright** | npm（dev） | ✅ | **高**（内建 `waitFor*` 自动重试） | 官方支持，`install --with-deps chromium` 一行 | ✅ **推荐** |
| Puppeteer | npm（dev） | ✅ | 中（需手写等待） | 需自行处理 chromium | ⬜ 不选 |
| 无头 Chrome 直调（`--dump-dom`） | **零 npm** | ✅ | **低**（虚拟时间与 async fetch 时序不可控） | ubuntu 自带 chrome | 🟡 备选 |
| jsdom / happy-dom | npm（dev） | ❌ **不支持完整 WebAssembly** | — | — | ❌ 不可行 |

### 1.2 推荐：**Playwright（仅 chromium）**

**判断依据（四条，按权重）**：

1. **稳定性优先（权重最高）**
   自动验证如果不稳定，**它本身就会变成新的噪音源**。本项目的教训很清楚：
   `l4.rs` 未入库导致 CI 连续约 22 次全红——验证环节的脆弱会直接摧毁交付节奏。
   Playwright 内建 `waitForFunction` / 断言重试，**专治 wasm 首帧异步**这类时序问题。

2. **必须真实浏览器**（硬约束）
   被验证的对象是 **WASM 应用**：jsdom 类方案无法执行 WebAssembly → 直接排除。
   因此只有"真实浏览器内核"可选。

3. **实测证据（本机）**
   我用系统自带 Edge 做无头 `--dump-dom` 实测：**120 秒超时失败**（重试亦不稳）。
   这证明"直调系统浏览器"在真实环境里不可靠；而 Playwright **自带 chromium**，
   不依赖系统浏览器是否存在、版本是否兼容 → 可复现性更高。

4. **不破坏零依赖红线**
   这是 **devDependency（测试工具）**，不进入任何产物、不进入内核代码。
   `meta-kernel-core` / `npb` / 网关**仍是零第三方依赖**。
   只安装 `chromium` 单浏览器（不装 firefox/webkit），体积与耗时可控。

> **为什么把"零 npm 依赖"排在稳定性之后**：
> 项目哲学的"零依赖"针对的是**产物**（内核、桥、网关必须能在无网络、无包管理的环境里构建运行）。
> 验证工具**不服务于产物运行**，只服务于**我们自己的交付纪律**——为它牺牲稳定性是不划算的。

## 2. 断言深度（系统自判）

### 2.1 候选层级

| 层级 | 做法 | 评价 |
|---|---|---|
| **L0** 只断言元素存在 | 检查 DOM 里有"诊断台"字样 | ❌ **无意义**：静态 `index.html` 里本来就有，**wasm 没跑也能通过**（假绿） |
| **L1** 断言动态渲染结果 | 注入构造数据 → 断言 wasm 执行后才出现的**动态内容**（亢/枯/平、确信度、溯源、多语言正文） | ✅ **推荐** |
| **L2** 截图对比 | 与基准图做像素 diff | ❌ 脆性高（字体/渲染差异），维护成本 > 收益 |
| **L3** 交互链路测试 | 点按钮切视图、走完整"念头→诊断"链路 | 🟡 二期（价值高，成本也高） |

### 2.2 推荐：**L1（动态渲染断言）**

**理由**：

1. **它才能证明"wasm 真的在运行"**——这是 L0 完全证明不了的（L0 是假绿）。
2. **与产品价值直接对应**：用户看到的就是"诊断结论"，断言的正是它。
3. **引入确定性**：CI 里先 `POST /v1/probe` 注入一条**构造的场域向量**
   （如 `[2,2,2,1,1,1,1]` → 火亢），于是页面上应出现的结论是**可预测的**，
   断言有明确依据（不是"看到什么都算过"）。
4. **不引入脆性**：只断言文本/元素，不做像素比对。

**二期可选**：L3 交互测试（点击「设置」页切换、授权链日志渲染等）——待 L1 稳定后再加。

## 3. 运行频率（系统自判）

| 时机 | 是否运行 | 理由 |
|---|---|---|
| **每次 push / PR** | ✅ **跑** | 这是"目验"环节，属于**每次交付都该过的门**；成本仅约 40–60 秒 |
| 定时（nightly） | ⬜ 暂不 | 当前规模不值得；待引入多浏览器/交互测试后再考虑 |
| 手动（workflow_dispatch） | ✅ 已具备 | 现有 ci.yml 已支持手动触发 |

## 4. 实现路径（系统自判）

```
① 拼装 dist/            manifest-ui/index.html + 注入 module script -> manifest-ui/dist/index.html
                                    ↓
② 起网关（同源托管）      npb-gateway <port> --ui manifest-ui/dist
                                    ↓
③ 注入构造场域数据        POST /v1/probe  {"schema":1,"s":[2,2,2,1,1,1,1]}   → 火亢（可预测）
                                    ↓
④ 真实浏览器访问并等待    Playwright(chromium) -> goto(url) -> waitForFunction(出现"确信度")
                                    ↓
⑤ 断言 + 截图存档        标题/视图标签/四元状态字/确信度/溯源/建议 + fullPage 截图
                                    ↓
⑥ 失败即红              任一项不过 -> exit 1（不静默跳过）
```

**本地运行**（三步）：

```bash
# 1) 准备产物
cd manifest-ui && wasm-bindgen target/.../manifest_ui.wasm --out-dir dist --target web
#    （并把 index.html 注入 module script 后复制到 dist/）

# 2) 起网关
./target/debug/npb-gateway 3210 --ui manifest-ui/dist &

# 3) 注入数据 + 目验
curl -X POST http://127.0.0.1:3210/v1/probe -H 'Content-Type: application/json' \
     -d '{"schema":1,"s":[2,2,2,1,1,1,1],"at":"local"}'
cd examples/ui-verify && npm install && npx playwright install chromium
UI_URL=http://127.0.0.1:3210/ node verify.mjs
```

**CI 集成点**：紧接现有步骤「Manifest UI wasm 前端构建（wasm-bindgen，产物=dist/）」之后
（该步骤已产出 `dist/manifest_ui.js` 与 `dist/manifest_ui_bg.wasm`，只需再补 `dist/index.html`）。

**降级策略**：若浏览器不可用或安装失败，步骤**明确失败并打印原因**——
不静默跳过（静默跳过等于把"待用户目验"偷偷塞回来，违背本次整改目的）。

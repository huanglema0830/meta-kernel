# 云内核项目 · 对话与报告模板

> 本文件是**三方（用户 / 顾问 / WorkBuddy）对话格式的单一约定**。
> 目的：把"每次重新对齐"变成"基准持续存在"，把"等人就停滞"变成"无响应自动推进"。
> 目录：§〇 固定相与活相｜§一 指令模板｜§二 报告模板｜§三 优先级机制｜§四 无响应推进机制｜§五 断裂接续机制｜§六 讨论记录模板｜**§七 变更记录（活相机制）**｜**§八 顾问简报更新流程**｜**§九 决策评估模板（顾问用）**

## 〇、固定相与活相

| | 固定相（骨架） | 活相（内容） |
|---|---|---|
| **是什么** | 指令/报告**必须出现**的话术项，一项都不能少 | 每项里写什么、写多细，随任务调整 |
| **能不能改** | 只能由**用户确认**后改（走 C8 / §活相机制） | 可自由增删、试错 |
| **为什么固定** | 少一项 → 就会退回到"只报现象不给全貌 / 只问是非题 / 把决策裸推给用户" | 任务千差万别，内容必须能变 |
| **记账** | 变更写入 `TEMPLATES_CHANGELOG.md` | 观察与提议写入 `OBSERVATIONS.md` |

### 固定相 A：**指令必带八项**（顾问 → WorkBuddy）

1. **基准**（先读 BASELINE.md）
2. **约束**（按 CONSTRAINTS.md 执行）
3. **总规划定位**（当前处于总路线图的哪个阶段/子任务）
4. **任务类型**（功能 / 修复 / 调研 / 清理 / 机制）
5. **本阶段目标**（一句话）
6. **任务内容**（具体）
7. **验收标准**（逐条可判定）
8. **汇报格式**（按报告模板）

> 另**必须附**：版本号自动生成、不手写（C2）。

### 固定相 B：**报告必带十一项**（WorkBuddy → 顾问）

1. **基准**（BASELINE 已更新/未更新）
2. **总规划定位**
3. **任务**
4. **状态**（完成 / 部分完成 / 未完成）
5. **验收对照**（标准 vs 实测，逐条）
6. **未完成项**（清单 + 原因）
7. **真实缺陷**（本次发现的）
8. **三量台账**（存量 / 变量 / 补充增量 / 创新增量）
9. **边界说明**（本地跑过 / CI过 / 真实跑过 / 未验证）
10. **需要用户决策**（清单）
11. **下一步建议**（清单）

> **纪律**：第 8、9 项**不得省略**（对应 C5/C6）；
> 报告里**不得出现手写"当前版本"**——版本一律来自 `git rev-list --count HEAD`（C2）。

## 三、优先级机制

```markdown
- P0：阻塞性任务（不做后续全卡）
- P1：需要决策才能做
- P2：需要验证才能做
- P3：无需决策，可自主推进（调研/文档/测试/重构/修复/清理/基准维护/CI优化）
- P4：低优先级优化
```

**P3 清单（不等人的活）**：
- 调研类：技术调研、依赖调研、方案对比、前沿搜索
- 文档类：文档撰写、注释补充、架构图更新、README更新
- 测试类：补充单元测试、增加覆盖率
- 修复类：修复已知缺陷（不涉及架构变更）
- 清理类：技术债清理、警告消除、死代码移除
- 基准维护：BASELINE.md更新、ROADMAP.md更新、报告归档
- CI优化：加速CI、增加断言、优化缓存

> **与 C4 的关系**：C4 要求"改前先列清单、确认后执行"。**P3 项不含架构变更**，
> 故可在清单已列明的前提下直接推进；一旦触到 A 类改动（界面/核心交互/表结构/删除覆盖迁移/元规则），
> **降级为 P1 并停下等确认**，不得以"无响应"为由越界。

## 四、无响应推进机制

```markdown
**P1/P2 处理流程**：
T+0：发出请示
T+30min：第一次提示
T+2h：第二次提示（标注"超时未响应"）
T+4h：判定为"暂时无响应" → 转向 P3 清单
用户回来后：优先处理等待决策的事项
```

> 原则：**提问不等于停下**。请示照发，手里的 P3 照做，两边不互相阻塞。

## 五、断裂接续机制

```markdown
**每次对话开始，WorkBuddy 按顺序读**：
1. coordination/CHARTER.md — 全部机制总入口（先看全貌）
2. coordination/BASELINE.md — 项目当前状态
3. coordination/CONSTRAINTS.md — 硬约束
4. coordination/TEMPLATES.md — 模板格式
5. coordination/ROADMAP.md — 总路线图
6. coordination/instructions/ 最新文件 — 当前任务
7. coordination/reports/ 最新文件 — 最近报告

**每次报告结束，WorkBuddy 必须**：
1. 更新 BASELINE.md（如果版本变了）
2. 把本次报告归档到 reports/
3. 把本次指令归档到 instructions/（如果是指令触发的）
4. 如有讨论记录，归档到 discussions/

**任何一方断裂，接续话术**：
> 继续云内核项目。读 coordination/ 下的最新状态。
> 告诉我：当前到哪一步、下一步是什么、需要我决策什么。
```

## 七、变更记录（活相机制 · 一个文件搞定）

> **设计口径（2026-09-16 简化）**：机制本身不能成为负担。
> 原先把"模板可变化"这件事拆成 `TEMPLATES_CHANGELOG.md` + `OBSERVATIONS.md` 两个**独立文件**维护，
> 评审判定为**过度设计**——一个"机制怎么活"的机制，不需要三个文件。
> ⇒ 本轮合并：两个旧文件**已删除**，内容并入本节；**程序保留**，只是不再单独立文件。
> （删除不丢历史：旧文件在 git 历史里可追溯，本节亦记明合并来源。）

### 7.1 变更程序（提议 → 试用 3 轮 → 生效/废弃）

```
任意一方提议（用户 / 顾问 / WorkBuddy 均可）
   ↓  在 §7.2 表里**加一行**：提议方／时间／类型／内容／理由／状态
   ↓  立即在 TEMPLATES.md 正文把该项标注"试用中"
   ↓  试用 3 轮（观察：是否真被用到？是否真解决问题？）
   ↓  回顾：
       有效 → 去掉"试用中"，标注 ✅ 生效
       无效 → 标注"已废弃"（**保留该行**，3 轮后再删）
       需调整 → 改那一行，重新计时
```

**变更类型**：新增字段／调整阈值／撤销字段／调整约束（走 C8）／调整子任务（改 `ROADMAP.md`）。

## 八、顾问简报更新流程

**触发条件**（用户说）：**「这段讨论落库」**／**「归档」**／**「更新顾问简报」**。

**动作（WorkBuddy 四步）**：

1. **提炼结论**——只写**结论与影响**，不写过程；**不写算法细节**（分层保密，见 `workflows/universal_workflow.md`）。
2. **更新 `coordination/advisor_brief.md`**：
   - §二 当前阶段（**变了才改**）
   - §三 最近讨论结论——**按时间倒序，硬上限 5 条**（新条目插最前，最旧的挤出去）
   - §四 待决策项（新增 / 关闭）
   - §五 方向判断（**有变化才改**）
   - 首行「最后更新于：HEAD xxx」（快照口径，C2）
3. **归档讨论**到 `coordination/discussions/`（格式用 **§六 讨论记录模板**）。
4. **同步 `BASELINE.md`**（有 R 编号 / D 编号变化时）。

**去重原则（重要）**：

| 文件 | 定位 | 回答的问题 |
|---|---|---|
| `advisor_brief.md` | **滚动摘要**（≤5 条） | **"现在到哪了"** |
| `discussions/` | **完整历史** | "当时怎么想的" |

**两者不重复**：brief 只保留**当前仍然有效**的信息；过期结论移出 brief（但历史仍在 discussions 里，不丢）。

**为什么设 5 条上限**：brief 的唯一用途是"**读一份就能接续**"。
一旦无限增长，它就退化成第二个 `reports/`，**失去接续价值**。

## 九、决策评估模板（顾问用）

> 对应 **C11**。**适用范围：顾问侧**（不是 WorkBuddy 侧）。
> 一句话：**凡涉及决策，顾问必须按此格式给全，然后停下来等用户决策。**

```markdown
【决策评估】
- 事项：X
- 评估：背景和现状
- 优势：至少 2 条，具体到可验证
- 劣势：至少 2 条，具体到可验证
- 风险：至少 2 条，标注概率和影响
- 建议：明确推荐哪个选项，附理由
- 等待用户决策
```

**当选项多于 2 个时，加「各选项对比」表**：

| 选项 | 成本 | 风险 | 收益 | 可逆性 |
|---|---|---|---|---|
| A | … | … | … | … |
| B | … | … | … | … |

### 硬要求（缺一即不合规）

1. **优势 / 劣势 / 风险 各至少 2 条**，且**具体到可验证**（不许写"更好/更稳"这类不可验证的话）。
2. **风险必须标注概率与影响**（🔴高/🟡中/🟢低 × 影响面）。
3. **建议必须是明确的**（"推荐 A，因为…"），**不许把选项原样抛回给用户**当决策。
4. **结尾必须是「等待用户决策」** —— 用户决策前，**顾问不得擅自执行**；决策后由 WorkBuddy 按用户决策执行。

### 与 WorkBuddy 侧的关系（两套并存，勿混）

| 场景 | 用哪套 |
|---|---|
| **顾问 → 用户** | 本模板（C11）：评估／优势／劣势／风险／建议／等待决策 |
| **WorkBuddy → 用户** | 用户跨项目「决策呈现规范」：相关点全列／风险点（含不做的风险）／经验教训／好处／不同做法差异／继续往前的推荐 |

**共同底线**：不许只问"做不做"、不许把决策裸推给别人、不许以提问为由停摆。

## 一、L7 设计稿内容

### 1.1 定位

- **L7 = 执行层**。
- **对内**：**激发修复场** —— 将问题映射为「**场参数**」。
- **对外**：**多内核互联 + 修复执行**（**双模式**）。
- **触发**：**静默监听** —— 只在收到 L6 明确执行信号时才唤醒。
- **决策权**：**在用户** —— L7 只提供方案，不决定"要不要做"。

> **与既有底图的关系（本稿的定位建议）**：既有 `L7_EXECUTION_DESIGN` 把 L7 定义为「**多内核互联** ＋ **修复执行**（动作分级 T0–T3）」；本稿的「问题-场参数映射」应被理解为**修复执行的上游"翻译层"**：
>
> ```
> 问题（结构化）→ 【问题-场参数映射｜本稿】→ 场参数配置 → ┬─ 场能模式（信息层）
>                                                          └─ 物理模式（需硬件，远期）
>                                                          ↓
>                                       既有 L7 纪律：T0–T3 分级 + 用户确认 + 哈希链记账
> ```
>
> 即：**本模块只产出"参数"，不产出"动作"**；"要不要做"仍走既有分级与确认链。

### 1.2 L7 对内：问题-场参数映射

- **接收**：L6 传来的**结构化问题**（见 §1.6）。
- **输出**：一个「**修复场**」的参数配置（下称 `FieldPlan`）。
- **参数可能包括**：场的**强度、梯度、作用范围、频率**等（发起指令所列）。

> ★ **口径建议（C19：同一机器事实只许一份口径）**：项目**已有**权威的场表述 —— `docs/FIELD_REPAIR_DESIGN.md` 的**七维场域状态向量** `S = (t, f, a, φ, x, H, τ)`。建议**不另立一套场参数**，而是让 `FieldPlan` **以七维为骨、以施加参数为用**：

| `FieldPlan` 字段 | 来源 / 口径 | 说明 |
|---|---|---|
| `target_dims` | 七维子集（t/f/a/φ/x/H/τ） | 判定「损伤维」＝哪些维偏离超限 |
| `delta` | `Δ = S_now / S_base`（逐维） | 偏离量（>1 亢、<1 枯） |
| `compensation` | `S_c ≈ S_base² / S_now`（逐维） | **补偿场**，反相而非加能量 |
| `apply_params` | **本稿新增**：强度 / 梯度 / 作用范围 / 频率 / 时长 / 相位 | 施加装置的参数（发起指令所列四项**归位于此**） |
| `iterations` / `residual` | 收敛判据 `|Δ| ∈ [0.618, 1.618]` | 迭代与残差 |

- **借鉴**：**CEMI 场理论**（大脑作为**混合数字-电磁场计算机**）——作**架构参照**（信息维＋场维的双表示）；
- **启发框架**：**张祥前统一场论**——**仅作启发性框架，不作工程实现的直接公式来源**（见 §1.8）。

### 1.3 L7 对外：双模式执行

| 模式 | 内容 |
|---|---|
| **场能模式** | 对于**信息层面**的问题，直接通过场的作用"解决" |
| **物理模式** | 对于**物理层面**的问题，驱动智能机器人去执行物理动作 |

> **与既有底图的接口对齐**：`docs/FIELD_REPAIR_DESIGN.md` §2.5 已**预留**统一执行接口 `apply(action) -> Result<Effect, Unsupported>`，并在**无硬件时一律 `Unsupported`**。
> ⇒ **场能模式** = 该预留接口的**未来实现**（当前 `Unsupported`）；**物理模式** = 依赖外部设备，**远期**。
> ⇒ **两模式都不绕过**既有 L7 纪律：任何写作用仍走 **T0–T3 分级 + 用户确认 + 哈希链记账**。

### 1.4 L7 触发：静默监听

- 无明确任务时，处于**极低功耗**的监听状态；
- **只"感"不"应"**；
- 只有收到 **L6 明确执行信号**时，才被唤醒；
- 遵守「**不侵**」戒律 —— **不主动干涉**。

> ★ **落地建议（机制 21 执行体边界）**：「监听」需要**感知**（事件/时间）⇒ **只能宿主侧**；**纯算层**只应承载**纯函数**（`问题 → FieldPlan` 的映射）。本稿 §1.7 建议的落点即按此划分。

### 1.5 L7 用户确认

- 提供「**思路**」或「**执行**」**两种方案**；
- 最终**决策权在用户**；
- **L7 本身不决定"要不要做"，只决定"怎么做"**。

> **复用既有机制**：L6 已实现**授权链**（关键操作 `confirm` ＋ 追加式授权日志 ＋ 设置页撤销，落点 `manifest-ui`）。本模块**直接复用**，不新造确认通道。

### 1.6 与 L6 的接口

- **L6 → L7 传入**：**结构化问题** ＋ **执行模式**（`ProvideSolution` / `ExecuteAuthorized`）。
- **L7 → L6 传出**：**修复场参数**（`FieldPlan`） / **动作指令**。

| 执行模式 | 语义 | 建议走既有哪条链 |
|---|---|---|
| `ProvideSolution` | 只出**思路**（不执行） | 等价于"**只出建议**"（不进入写作用） |
| `ExecuteAuthorized` | 已获**授权**的执行 | 进入既有 **T1/T2 确认链**（`grad / grant / execute`） |

> ★ **接口纪律提示**：若这两个模式枚举**要进治理表**（如 `TERMS.md` 或编号表），须走 **C15 双向计数**；本稿**不自行登记**。

### 1.7 与现有代码的关系（**已按实测订正** —— 详见 §〇）

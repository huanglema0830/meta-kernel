# 问题1 · L4-V1 裁定稿

## 1.0 前提修正（这条比三方案本身更重要）

上轮我把 L4-V1 定性为「**循环依赖**」：L4 判定要基线 → 基线是本底场 → 本底场是 L5 产物 → 冷启动死循环。

**本轮逐行查证后，这个定性不成立。** 底图中 L4 的「基线」**并非必然来自 L5**，它至少有 **3 个已存在的来源**：

| 来源 | 底图原文 | 位置 |
|---|---|---|
| ① **单位基线（七维全 1.0）** | 「测试方法：`l4_router::route_with_baseline(向量, 健康基线)`；**基线 = 七维全 1.0**」 | `L4_VALIDATION_REPORT.md` 行5 |
| ② **基因库基础公式层** | 「L4 的判定公式（`1.618` / `0.618`）**来自基因库的基础公式层**——不是硬编码的外部常数」 | `LAYER_ARCHITECTURE.md` 行200–201 |
| ③ **L5 本底场（场景公式）** | 「本底场（v1.4）：由"数据存储"升级为**场景公式**（按场景分类存储）…来源＝基因库场景公式层」 | `LAYER_ARCHITECTURE.md` 行222–223 |

**所以真问题不是"循环依赖"，而是：「基线」这个词在底图里有 ≥3 个来源，但没有任何一处定义「什么时候用哪一个」。** 三方案因此从"打破循环"变为"**定义基线来源的选取规则**"。

> 这一修正**降低**了问题严重度（不死循环），但**不改变**它必须被裁定的必要性——因为 L4 是拒绝层，基线选错会直接导致误拒（不非时食/不捉持），误拒的数据**被丢弃不缓存**（`SILA_IMPLEMENTATION.md` 行68），不可恢复。

## 1.1 六要素（先摆全，不只问"做不做"）

**① 相关的点**
- 上游：L3 语义事件 + 七维 `S=(t,f,a,φ,x,H,τ)`（`LAYER_ARCHITECTURE.md` 行202）
- 本层：`route_with_baseline(向量, 健康基线)` → Pass / `UnseasonalMeal` / `Ungrasping`
- 下游：L4 Pass 才进 L5；**被拒即丢弃**（无缓存、无残留，`L4_VALIDATION_REPORT.md` 行18–21）
- 牵连：场修复用 `Δ = S_now / S_base`（`FIELD_REPAIR_DESIGN.md` 行55），**修复侧也依赖同一基线** ⇒ 基线口径影响 L4 与场修复两处

**② 风险点（含"不做"的风险）**
- **做错的风险**：基线取"全 1.0"而对象本底本就偏离 1.0（实测老笔记本 `s=[0.099,1,1.15,1,1.294,1.83,6.587]`，H=1.83、τ=6.587 天然 >1.618，`L5_VALIDATION_REPORT.md` 行93–95）⇒ 该机器**每次都会被判不非时食**，L5 永远收不到数据。
  ⚠️ 注意：实测记录显示该机器 L4 判 **Pass**——因为"high=2/7，不足 3 维"（行95）。**只差 1 维就越线**。这是真实风险，不是假想。
- **不做的风险**：L4 的基线来源随实现者心情决定 ⇒ 同一对象在不同版本判定结果不同 ⇒ 违反「可复现」（L5 不妄语戒律，`SILA_IMPLEMENTATION.md` 行79）。

**③ 经验教训**
- 上一课（本轮）：**"没找到" ≠ "不存在"**——不要把"我在一份文件里没找到"写成"全库无定义"。
- 上一课（v0.192）：**本机绿 ≠ CI 绿**——判据只在本机能过，是因为本机有仓库外的 MEMORY 兜底。
- 底图自身的先例：A5 作用域问题（`MATH_SPEC` 行46 vs 行48–51）是用「**加收敛说明**」而非「改原文」解决的——**先例倾向于"补口径"，不重写**。

**④ 好处（可衡量）**
- 判定可复现：同一对象+同一场景 ⇒ 同一结论（可被自动化测试锁定）
- 误拒率可测：能统计"被 L4 拒绝的次数 / 总次数"，当前无法统计（基线不定）
- 冷启动可定义：新对象首次接入时行为明确，不再依赖实现者

# 问题2 · L6-V2 未显化查证稿

## 2.0 发起人问的三件事，逐条回答

### 问：从底图取"回执"的原文定义（`SILA_IMPLEMENTATION.md` §2 L6 行 89）

**原文（逐字，行89）**：
> 「- **不妄语·校准**：显化产物需能被真实世界"接受/执行/回执"，否则视为未显化（防自说自话闭环）；世界通道加可信校验，拒绝伪造反馈输入。」

### 问：回执是什么？

**准确答案是分两层的**——这是本次查证最关键的一点：

| 层 | 位置 | 给了什么 |
|---|---|---|
| **判据意义** | `SILA_IMPLEMENTATION.md` 行89 | 回执是**判据**：显化产物必须能被真实世界接受/执行/回执，**否则视为未显化**。⚠️ 这一行**没有定义回执是什么**，只定义了"没有回执的后果" |
| **数据结构定义** | `archive/reserved-interfaces/l6_interface.rs` 行14–18 | **有完整定义**（见下） |

**回执的完整定义（逐字，l6_interface.rs 行12–18）**：
```rust
/// 世界回执：L5 外显被真实世界接受/执行/完成的状态。
pub struct WorldReceipt {
    pub entry_id: String,
    pub status: &'static str, // "accepted" | "executed" | "completed" | "rejected"
    pub at: u64,
}
```
配套（行22–25）：
```rust
pub trait WorldAdapter {
    fn deliver(&self, entry: &...ManifestEntry) -> Result<WorldReceipt, String>;
    fn verify_receipt(&self, r: &WorldReceipt) -> bool;
}
```

**所以，对发起人"如果底图里没有回执的定义，明确写底图中无定义"这一问的回答是：**
> **底图里"有"回执的定义，但它不在发起人指定的 `SILA` 行 89 —— 它在 `archive/reserved-interfaces/l6_interface.rs` 行12–25。**
> `SILA` 行89 只有**判据意义**（无回执⇒未显化），**没有**数据结构定义。
> 这两处**没有互相引用**（SILA 未指向该契约文件；该文件头只引用 LAYER_ARCHITECTURE 与 SILA 的"对齐机制"）⇒ **存在"定义与判据分居两处、互不可见"的真实不足**。

### 问：为什么"未实现的对齐子功能"会导致"未显化"？

**因果链（全部有底图出处）**：

```
① L6 = 呈现 + 对齐 两个子功能        ⟨LAYER §4 L6, 行240-245⟩
                    │
② 对齐 = 接收外部世界反馈，验证诊断是否生效（投递/回执/校准）
   实现状态：❌ 未实现                 ⟨LAYER §4 L6 表, 行245⟩
   落点：WorldAdapter，契约见 archive/reserved-interfaces/l6_interface.rs
                    │
③ 该契约文件头明确："NOT COMPILED"、"本文件为愿景契约…不编译"
                                      ⟨l6_interface.rs 行2、行9⟩
                    │
④ ⇒ 目前没有任何通道能把 L5 外显产物投递出去，也没有通道能收回 WorldReceipt
                    │
⑤ SILA 行89 判据：显化产物需能被真实世界"接受/执行/回执"，否则视为未显化
                    │
⑥ ⇒ 结论：按底图自身判据，当前系统处于「未显化」
```

**一句话**：回执只能由 `WorldAdapter::deliver()` 产生；而 `WorldAdapter` 未实现（契约不编译）⇒ 收不到回执 ⇒ 按行89 ⇒ 未显化。

## 2.1 发起人方案「让用户确认一次」——能不能解？

发起人原话：「如果回执=用户确认，解法是让用户确认一次，不是改底图。」

**查证结论：不能直接解，需要一个额外的映射规则。三条理由：**

| # | 理由 | 出处 |
|---|---|---|
| 1 | 用户确认若发生在 `manifest-ui`（呈现侧），它**不经过** `WorldAdapter::deliver()`，产生的不是 `WorldReceipt` | `l6_interface.rs` 行22–23 |
| 2 | `WorldReceipt.status` 的四态是 accepted/executed/completed/rejected ——"用户在自家 UI 上点确认"最接近 `accepted`，但 `accepted` 的语义是"**真实世界**接受"，而自家 UI **不是真实世界**（是自家呈现层） | `l6_interface.rs` 行15 |
| 3 | ⚠️ SILA 行89 还有后半句：「**世界通道加可信校验，拒绝伪造反馈输入**」——手工确认若不经 `verify_receipt()`，恰恰落在"伪造反馈"的射程内 | `SILA` 行89 |

**所以**：发起人的方向（"让用户确认一次"）**对**，但它**不是"不用改底图"，而是"必须补一条映射规则"**——即：**人工确认如何成为一份合法的 WorldReceipt**。

## 3.1 空白的确认（取证）

`MATH_SPEC.md` §1（行9–20）给了**三个引擎各自的公式与"含义"**，但**没有任何一处说"什么时候用哪一个"**：

| 引擎 | 公式（行10/14/18） | 含义（行11/15/20） |
|---|---|---|
| 线性 Linear | `output = input + 0.01` | 惯性、恒常、**可预测的平稳消耗** |
| 斐波那契 Fib | `output = (a + b) * 0.5`（a,b = 前两次输出） | 生长、自相似递归、**基于历史的自我参照** |
| 指数 Expo | `output = input * e^(λ * Δt)`，`>0.99` 强制回退 0.5 | 临界、相变、**正反馈爆发与自抑制** |

补充参数：`A2`（行43）Fib 真空态(0,0) 首次正输入点燃递归；`A3`（行44）Expo `λ=0.25`、`Δt=1.0`。

全库检索「线性|斐波那契|指数」：**无任何一处给出选取规则**。`LAYER_ARCHITECTURE.md` 行165 只列"三变化模式引擎"为 L1 功能，同样无选取规则。**空白属实。**

## 3.2 补齐稿：规则应该是什么（从底图取依据）

### ⚠️ 先排除一个错解：不能用「地水火风」选引擎

我上轮在 `LAYER_BASEMAP_L0_L6.md` 行222 提过"方案 A（语境驱动）：风→指数、火→斐波那契、水→线性、地→线性"，依据是 `PERTURBATION_MODEL` §3 四行表。

**本轮查证发现该方案违反底图**——`PERTURBATION_MODEL.md` 行63 逐字：
> 「行属性**不改变内核数学**（内核仍按能量流演化——守"界面=投影"）；只供上层（L4 命名/意图、L5 日志）选择表达口吻与预期。」

四行是**上层投影用的语义标签**，用它去决定 L1 内核用哪个引擎 ＝ 让投影反作用于内核数学。**排除。**

### ✅ 合规解：由**内核自身的状态量**决定（不引入外部/上层语义）

可取依据有二，**都是内核自身的量**：

| 依据 | 底图出处 | 内容 |
|---|---|---|
| **物态判据** | `GENE_LIBRARY_DESIGN.md` §2.1 行61 | 「物态判据：`入/出 > 1.2 → 能量态；> 1.05 → 气态；≥ 0.8 → 液态；< 0.8 → 固态`」 |
| **三引擎语义** | `MATH_SPEC.md` 行11/15/20 | 平稳消耗 / 基于历史的生长 / 临界相变 |

**⟨拟补条文 · 待裁定⟩ L1 三引擎选取规则（建议稿）**

| 内核状态 | 选取引擎 | 依据（底图） |
|---|---|---|
| **固态**（入/出 < 0.8） | **线性** | 固态＝沉淀固化、变化最缓 ⇒ 配"恒常、可预测的平稳消耗"（MATH_SPEC 行11） |
| **液态**（0.8 ≤ 入/出 ≤ 1.05） | **斐波那契** | 液态＝平稳吸收、储备维持，且 Fib 依赖前两次输出（历史）⇒ 配"基于历史的自我参照"（行15） |
| **气态**（1.05 < 入/出 ≤ 1.2） | **斐波那契** | 同上，仍在可递推区间 |
| **能量态**（入/出 > 1.2） | **指数** | 能量态＝临界 ⇒ 配"临界、相变、正反馈爆发"（行20）；且 Expo 有 >0.99 回退 0.5 的自抑制护栏，正合"爆发与自抑制" |

**三条硬约束（防止补齐后产生新问题）**：
1. **不新增算子**：只做"选哪一个"，不改任一引擎公式 —— 守 `SILA` 行48「不饮酒：演化只允许三种算子……不做其它"调味算法"」。
2. **确定性可复现**：同一状态 ⇒ 同一引擎 ⇒ 跨平台摘要 `4251318995` 不变（`CREATION_LOG.md` 行24–25；`MATH_SPEC` 摘要红线）。
3. **边界不跳变**：物态在阈值附近抖动时，引擎切换不应导致输出跳变 —— 需要在阈值处**确认三个引擎输出连续**（线性 `+0.01`、Fib `(a+b)/2`、Expo `×e^0.25` 在边界处**不相等** ⇒ ⚠️ **存在跳变风险，须实测**）。

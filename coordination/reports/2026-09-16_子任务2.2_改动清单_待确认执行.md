## 〇、先说一条纠正：本步**不是**"接 GRUB 或 Limine"

原路线写的是"接入 GRUB / Limine 引导器"，侦察后**建议改口径**——见 §二 选型对比：

| 候选 | 与现状的匹配度 | 结论 |
|---|---|---|
| **`bootloader` crate 0.11**（rust-osdev） | ① **内核侧用 `x86_64-unknown-none` 即可**，**不需要自定义 JSON target、不需要 build-std**（官方 v0.9 迁移文档明写"no need for custom JSON-based target files anymore"）；② 提供 BIOS + UEFI 双引导；③ 产出可引导磁盘镜像**在 Rust 内完成**（`build.rs` 调 `bootloader` crate） | ★ **推荐** |
| **Limine** | 需引入**外置 limine 二进制** + `limine` crate + ISO 工具链；引导协议自定义（高层半区内核等），跨平台构建链更重 | 备选（若 `bootloader` 路线受阻） |
| **GRUB** | 需 `grub-mkrescue` / `xorriso`（Windows 上需额外安装或走 CI）；GRUB 是"引导器"，**不负责建镜像** | 留到 **2.7 ISO** 阶段 |

**⇒ 建议本步目标改为**：**"能被引导器引导"——以 `bootloader` 0.11 产出可引导 `.img` 为达成标志**；
GRUB/Limine/ISO 化（`xorriso`）留到 **2.7**。

## 一、🚨 先决条件（三条，必须先定，否则清单无法执行）

### 1.1 **需要 nightly**（本机目前**只有 stable**）

**实测**：`rustup toolchain list` → 只有 `stable-x86_64-pc-windows-gnu` / `stable-x86_64-pc-windows-msvc`；**无 nightly**。
**外部事实（有出处）**：`bootloader` 0.11 的官方文档写明
> "You need a **nightly Rust compiler** with the **llvm-tools-preview** component"

**关键区分**（这决定成本）：
- **内核本身** → 用 `cargo build --target x86_64-unknown-none`（**预编译 core，stable 可用**）✅
- **引导器二进制 + 镜像打包**（`bootloader` crate 内部会调 `-Zbuild-std`）→ **需要 nightly** ⚠️

### 1.2 **C1（内核零依赖）的解释边界**

新建 crate 必须引 `bootloader_api`（内核与引导器**必须共享同一份 `BootInfo` 定义**，否则 UB）。
**请求明确**：`bootloader_api` 属**引导层**，**不进 `meta-kernel-core` / `meta-kernel-core-nostd`**（二者**保持零依赖**）。
→ 需你确认这一边界解释（记为 **D31-a**）。

### 1.3 **本机无 QEMU**

**实测**：本机未见 `qemu-system-x86_64`。而"**能被引导**"必须有**真运行**证据（C7：CI 过 ≠ 真跑）。
→ 需定 QEMU 落点（记为 **D31-c**）：**CI 装**（`apt-get install qemu-system-x86`，★推荐，零本机污染）／本机装（需你同意装软件）。

## 二、改动清单（预计新增 7 个文件、改动 2 个文件，**现在都不动**）

### 2.1 新增：`meta-kernel-boot/`（**独立 crate，不入 workspace**）

> **不入 workspace 的理由**：它与 `host/field-render` 同性质——**目标平台不是宿主**。
> 一旦入 workspace，`cargo build/test --workspace` 会在宿主上试图编译它 ⇒ **必然失败**。
> （代价：CI 的 `test` job **不会**跑到它 ⇒ **必须单独加一步**，这正是 **R18** 的教训。）

| # | 文件 | 作用 | 关键内容 |
|---|---|---|---|
| 1 | `meta-kernel-boot/Cargo.toml` | 包定义 | `dependencies`: `bootloader_api = "0.11"`, `meta-kernel-core-nostd = { path = "../meta-kernel-core-nostd" }`；`build-dependencies`: `bootloader = "0.11"`（`artifact = "bin"`, `target = "x86_64-unknown-none"`） |
| 2 | `meta-kernel-boot/rust-toolchain.toml` | **把 nightly 关在本目录** | `channel = "nightly"` ＋ `components = ["rust-src", "llvm-tools-preview"]` ⇒ **workspace 其余部分仍用 stable**（关键：避免整仓被迫上升 nightly） |
| 3 | `meta-kernel-boot/.cargo/config.toml` | crate 级构建配置 | `[build] target = "x86_64-unknown-none"`；`[unstable] bindeps = true`（artifact 依赖所需） |
| 4 | `meta-kernel-boot/src/main.rs` | **入口** | `#![no_std] #![no_main]` ＋ `bootloader_api::entry_point!(kernel_main)`；`fn kernel_main(boot_info: &'static mut BootInfo) -> !`；**在入口内调用 `meta-kernel-core-nostd` 做一次可判定计算**，把结果写进 framebuffer |
| 5 | `meta-kernel-boot/src/panic.rs` | **panic handler**（`no_std` bin 必需） | `#[panic_handler] fn panic(_: &PanicInfo) -> ! { loop {} }`（**先不死循环静默**：写入一个"失败色块"再停，便于 QEMU 判定） |
| 6 | `meta-kernel-boot/src/verify.rs` | **可判定输出** | 往 `BootInfo` 的 framebuffer 写**已知图案**（见 §三 路线 A），**只用安全 API** |
| 7 | `meta-kernel-boot/build.rs` | **产可引导镜像** | 调 `bootloader::BiosBoot::new(&kernel).create_disk_image()` → 输出 `boot-bios.img`（UEFI 版可选） |

> ⚠️ **待执行时验证的两点（现在不敢断言，C5）**：
> ① `bootloader` 0.11 是否需要自定义 `linker.ld`（官方说"若用 linker script，别改入口名"，暗示**默认可不用**，但需首次构建确认）；
> ② `bindeps` 是**不稳定特性**，nightly 版本差异可能导致 API 漂移 ⇒ 若受阻，**降级方案**：`build.rs` 里用 `Command::new("cargo")` 显式构建内核（官方文档亦给出此备选）。

## 三、验证方式（两条路线，**★推荐 A**）

| 路线 | 做法 | 是否需 unsafe | 可判定性 |
|---|---|---|---|
| **A 帧缓冲 + QEMU screendump**（★） | 内核向 `boot_info.framebuffer` 写**已知图案**（走廊／棋盘）；CI 起 `qemu-system-x86_64 -display none -monitor stdio` → `screendump out.ppm` → **断言 PPM 中指定坐标的 RGB == 期望值** | ✅ **零 unsafe**（framebuffer 是 Rust 安全 API） | 强（像素值可精确比对） |
| B 串口 COM1 | 内核写串口；QEMU `-serial stdio` 抓取 → 断言文本 | ⚠️ **需要** port I/O（`out` 指令）⇒ **走 C9**（白名单登记 + `// SAFETY:` 论证） | 强（文本可精确比对） |

> **建议先试 A**：能在**不触碰 C3/C9** 的前提下拿到"真运行"证据（C7）。
> 若 A 受阻（如 `-display none` 下 `screendump` 不可用 / 无 VESA 模式）→ 再走 B 并按 **C9** 申请白名单。
> **两条都行不通时的诚实结论**：本步只能做到"**能被引导器加载并进入内核入口**"，**须如实标注未真跑**（C5/C7）。

## 五、【决策评估】（C11 · 七要素）

- **事项**：2.2 的引导器选型 / nightly 引入范围 / QEMU 落点
- **评估**：2.1 已把内核做成 `no_std` lib 并能在 `x86_64-unknown-none` 上编译（**stable 即可**）。本步第一次需要"引导器 + 可引导镜像"，而这一环**官方明确要求 nightly**。本机**只有 stable**（实测）。同时本机**无 QEMU**，而 C7 要求"真跑"才算数
- **优势**（**确定的**）：① **内核侧零改动**——官方文档明确 `x86_64-unknown-none` **不需要**自定义 target / build-std，2.1 的成果**可直接复用** ② **nightly 可关在 boot crate 目录内**（`rust-toolchain.toml` 仅作用于该目录）⇒ workspace 其余部分**继续 stable** ③ 路线 A **零 unsafe**，不破 C3、不动 C9 白名单 ④ 产出 `.img` **在本机即可生成**，不依赖外置二进制（Limine/GRUB 需额外下载）
- **劣势**（**具体的**）：① 引入 nightly ⇒ **新工具链依赖**，且 `bindeps` 为不稳定特性（**有 API 漂移风险**）② boot crate 不入 workspace ⇒ 两处构建配置（**维护成本**，但已有 `field-render` 先例可循）③ 验收依赖 QEMU screendump 的可用性，**该行为我尚未实测**（本机无 QEMU）
- **风险**：① 🔴**高/中**：`bootloader` 0.11 与 **rustc 1.98 nightly** 的兼容性未知（该 crate 最新版 0.11.17 @ 2026-07）→ 应对：**首次构建即暴露**，受阻则降级 `build.rs` 走 `Command` 显式构建，或退回 Limine ② 🟡中/中：`screendump` 在 `-display none` 下可能不可用 → 应对：路线 B（需 C9 放行**一处** port I/O）③ 🟡中/低：nightly 污染 workspace → 应对：`rust-toolchain.toml` **只放 crate 内** ④ 🟢低/低：`.img` 体积偏大误入库 → 应对：`.gitignore`
- **机会**（**可能的**，附证伪条件）：① **2.5 的接口被提前打开**：一旦 `boot_info.framebuffer` 可用，**"内核 → 屏幕"的通道就通了**，2.4（DRM/KMS）可改为在**它之上**做，验收链条能提前打通 —— **证伪条件**：2.4 必须直接操作 DRM/KMS 而不经 bootloader 的 framebuffer ⇒ 该机会不成立 ② **CI 上首次出现"真执行而非真构建"的裸机验收点**（`hardware-free 真跑`），可复用于后续 2.3–2.7 —— **证伪条件**：QEMU 引导在 CI 上无法稳定复现（超时/渲染差异）⇒ 该机会退化 ③ `bootloader` 的 UEFI 路径可顺带验证 **UEFI 引导**，为 2.7 的 ISO 提供双路径 —— **证伪条件**：UEFI 版 `.img` 无法在无 KVM 的 CI 上启动
- **建议**：**选 `bootloader` 0.11（路线 A）**；**nightly 只在 boot crate 目录内生效**；**QEMU 装在 CI**。
  理由：① 官方文档**明确支持**我们现成的 `x86_64-unknown-none` 内核（**2.1 成果直接复用，零返工**）；② nightly 影响面可**精确限制在一个目录**；③ 路线 A 零 unsafe，**不破任何红线**；④ 三项成本（nightly／两份构建配置／CI 步骤）都**可逆且局部**
- **等待用户决策**

| 选项 | 成本 | 风险 | 收益 | 可逆性 |
|---|---|---|---|---|
| **`bootloader` + A 路线**（★建议） | 中（新 crate + nightly 局部化 + CI 步骤） | 中 | 内核零改动；零 unsafe；`2.4` 接口提前打通 | **高**（删 crate 即回退） |

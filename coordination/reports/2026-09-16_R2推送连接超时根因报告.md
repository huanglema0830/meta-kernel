## 〇、结论摘要（先给答案）

1. **"SNI 摩擦"这个命名不准确**——实测**不是 SNI 层拦截**。TLS 握手成功、证书 `subject=CN=github.com` 未被伪造。
2. 真实现象是 **TCP 连接建立阶段的间歇性超时**（`Failed to connect ... after 21092 ms: Could not connect to server`），**频率约 5%**（20 次 git 协议请求中 1 次）。
3. 一个**可复现的关联线索**：`GIT_TRACE_CURL` 显示 `schannel: remote party requests renegotiation`（服务器要求 **TLS 重协商**，单次请求里出现 2 次）——这是本项目所用的 **Windows Schannel** TLS 路径上的已知脆弱点。
4. 已找出**可根治方向**：**SSH over 443**（`ssh.github.com:443`）通道**实测可达**（能到认证阶段），可完全绕开 HTTPS + Schannel + 重协商。**切换动作涉及账号级配置，按 C10 待用户确认**（D19）。

## 一、排查方法（六批探针，全部为本机实跑）

| 批次 | 探针 | 目的 |
|---|---|---|
| A/B | 域名解析对比 + `hosts` 检查 | 排除 DNS 污染 / hosts 劫持 |
| C/D | TCP 连接（`/dev/tcp`）github.com 与 api.github.com，各多次 | 区分"TCP 层"还是"上层" |
| E | `openssl s_client -servername github.com` | 看 TLS 握手与证书主体（判 MITM / SNI 拦截） |
| F | `ssh -p 443 git@ssh.github.com` | 验证 SSH 通道是否可用 |
| G/H/I/J/K | `git push --dry-run` ×10、8 并发 TCP、90s 持续探针、`git ls-remote` 5+15 次 | 逼近真实 push 场景并**捕获失败现场** |
| L/M | `GIT_TRACE_CURL=1 git ls-remote`、`git --version` | 看协议层细节 |

## 三、逐条排除 / 定位

| 假设 | 判定 | 证据 |
|---|---|---|
| 走了代理（proxy 拦截） | ❌ **排除** | 环境无任何 `*_proxy` 变量 |
| DNS 污染 | ❌ **排除** | 解析到 GitHub 真实段 `20.205.243.x` |
| hosts 被改 | ❌ **排除** | hosts 无 github 条目 |
| **SNI 拦截**（旧命名来源） | ❌ **排除** | TLS 握手成功；证书 `subject=CN=github.com` 未被伪造；若 SNI 被阻断会在此处 RST，而非"连接超时 21s" |
| 证书被中间人替换 | ❌ **排除** | 同上（`subject` 正常；code 20 只是本机缺根证书） |
| api 与 github IP 段差异 | ❌ **排除** | 同一 /24 段 |
| 纯 TCP 层不可达 | ⚠️ **不能单独解释** | TCP 探针 12+8+12 = **32 次全成功** |
| **连接建立阶段的间歇性超时**（低频率） | ✅ **成立** | 表现为 21s 连接超时；`git` 协议层 20 次中 1 次失败；TCP 短探针难抓到 |
| **与 TLS 重协商相关**（Schannel 路径） | ✅ **强关联线索** | `GIT_TRACE_CURL` 显现服务器要求重协商；重协商正是"连接看似已建立、随后挂起/失败"的典型来源；`curl`（同样走 schannel）也出现同样的重协商提示 |
| SSH 通道不可用 | ❌ **排除** | `ssh.github.com:443` 到达认证阶段 |

**定位（诚实标注不确定度）**：
现象成立于 **TCP/TLS 连接建立 + 重协商**这一段，频率约 5%，**属间歇性**。
本机侧可做的区分已到极限——**无法进一步断定是"本地网络路径/运营商侧"还是"GitHub 边缘节点/中间设备"**
（需要抓包或从另一网络出口复测才能再切分）。**但对策不依赖这个切分**（见下）。

## 四、对策对比（六要素：成本 / 风险 / 收益 / 可逆性）

| 方案 | 成本 | 风险 | 收益 | 可逆性 |
|---|---|---|---|---|
| **A. 改用 SSH over 443**（`ssh.github.com:443`） | 生成一对 SSH key + 在 GitHub 账号添加公钥（**一次性，约 3 分钟**） | 需在账号内新增公钥（**账号级配置变更**） | **根治路径**：彻底绕开 HTTPS + Schannel + TLS 重协商；推送稳定性与速度均提升 | **高**：删除该公钥、`remote` 改回 https 即完全回退 |
| **B. 保持现状（HTTPS + 重试脚本）** | 0 | 每轮可能多花 5–15 分钟（本轮实测：第 2 次推送试了 **11 次、14 分钟**） | 已验证有效，无需任何配置动作 | — |
| **C. 显式固定 `http.version=HTTP/1.1`** | 一条 git config | 低 | 可能降低重协商触发（当前已是 1.x，收益存疑） | 高（unset 即回退） |
| **D. 换网络出口 / 挂代理** | 高 | 中 | 未知（可能只是把问题挪到别处） | 中 |

**我的推荐：A（根治）+ C（零成本互补）；在 A 落地前，继续用 B 兜底。**
※ A 需要你在 GitHub 账号侧添加公钥——**这一步按 C10 必须由你确认**（见 §五）。

## 一、mkosi 可行性（D2）

### 1.1 是什么
**mkosi = Make Operating System Image**，是 **systemd 项目官方子项目**，Python 编写，
本质是 **dnf / apt / pacman / zypper 的高级包装器**，用于从零生成**可引导**的 OS 镜像。

### 1.2 能生成可引导 ISO 吗
**能**，但注意它的**原生输出不是 ISO**：
| 输出格式 | 说明 |
|---|---|
| `disk`（raw GPT 镜像） | **可引导**（EFI + BIOS 均可直接启动），最常用 |
| `directory` / `tar` / `cpio` | 不可引导，用于容器 |
| `USI` / `UKI` | 统一内核镜像（可 Secure Boot 签名） |
| **ISO** | 需**二次封装**（mount 镜像 → `xorriso -as mkisofs` 生成 ISO） |

### 1.3 依赖
- **必装**：`mkosi`、`systemd-container`、`squashfs-tools`、`mtools`、`systemd-ukify`、`grub-pc-bin`
- **引导相关**：`systemd-boot`（EFI）／GRUB（BIOS）
- **建议**：文件系统支持 **reflink**（XFS / Btrfs），否则构建慢

### 1.4 ⚠️ 最大障碍：**mkosi 是 Linux-only**
- mkosi 依赖 `dnf/apt/pacman/zypper` + `systemd-nspawn`，**Windows 原生不可用**；
- 在**开发机（Windows）**上要跑，必须 **WSL2 + Linux 发行版**（apt 即可装 mkosi）；
- 生成的镜像是 **legacy-free**：**只支持 GPT 分区表（无 MBR）**、**只支持 systemd 发行版**；
  好消息是 **GPT 镜像在 EFI 与 BIOS 上都能引导**，故 2015 老机（BIOS 或 UEFI）**均可覆盖**。

### 1.5 替代方案（若不引入 WSL2）
| 方案 | 代价 | 适用 |
|---|---|---|
| **Alpine/Debian minimal + 手动打包 ISO**（`xorriso`） | 需 Linux 环境，但依赖极少 | **本项最轻** |
| 改造 Ubuntu LiveCD（`unsquashfs` → chroot → `mksquashfs`） | 镜像大（GB 级） | 快速出成果 |
| 我们已有的 **老笔记本实测通道**（`deploy/win64/` 一键包） | 零新增 | **当前最省**

## 二、裸机 DRM/KMS 渲染（D3）

### 2.1 参考项目（已核）
| 项目 | 做法 | 关键点 |
|---|---|---|
| **ZiCog/rust_embedded_wgpu**（发起人指定） | wgpu 优先 **Vulkan 直通 DRM**；失败则回落 **CPU 扫描输出** | CPU 回退：离屏渲到 RGBA8 纹理 → 回读 → 转 **XRGB8888** → 写 DRM dumb buffer → **KMS page-flip + 等 vblank**（双缓冲，无撕裂）。**该仓库同样踩过"请求 `adapter.limits()` 以支持大屏"**——与本项目既有经验一致 |
| **RealAdarsh/wgpu-drm-renderer** | 直接 **GPU→DRM framebuffer** | 双缓冲 + 硬件翻页；需 root 或 `video` 组权限；Vulkan 后端 |
| **Slint · LinuxKMS 后端**（**生产级先例**） | 三种后端：**wgpu+Vulkan（KHR Display 扩展）** / OpenGL via KMS-DRI / **软件（dumb buffer）** | 输入走 **libinput/libudev**，权限走 **libseat**（免 root）；依赖 `libgbm`／`libxkbcommon`／`libudev`／`libseat` |

### 2.2 依赖清单（Debian/Ubuntu 名）
`build-essential`｜`pkg-config`｜`libdrm-dev`｜`libudev-dev`｜`libseat-dev`｜`libgbm-dev`｜`libxkbcommon-dev`｜
`mesa-vulkan-drivers`｜`libvulkan1`｜`vulkan-tools`；可选 `kmscube`／`modetest`（调试）、`seatd`（免 root）

### 2.3 与本项目现状的**落差**（关键）
本宿主是 **`winit` + `egui-winit` + `wgpu`** 的**窗口式**架构，而 DRM/KMS 路径**没有窗口系统**：

| 现有件 | DRM/KMS 下的命运 |
|---|---|
| `winit` 开窗 / `ApplicationHandler` | **不可用**，必须换成 KMS 后端事件循环 |
| `egui-winit` | **不可用**；但 **`egui` 本身可离屏渲染**（`egui-wgpu` 渲进纹理）→ **UI 层可保留** |
| `wgpu` 渲染管线（三阶段） | **可复用**，只需把 target 从 surface 纹理换成离屏纹理 |
| 场域 → splat 全套内核逻辑 | **完全复用** |

→ **结论**：DRM/KMS 是**新增一个后端**（`host/field-render-kms`），**不是重写**。
UI 仍可用 egui 离屏渲染 → 与现有 egui 装配**同构**，改动可控。

## 三、2015 笔记本硬件适配（D4）

> ⚠️ **前置缺失**：**未提供具体型号**，以下为通用结论；准确结论需先采集硬件信息。
> **现成工具**：仓库 `deploy/win64/老笔记本-一键采集.bat` 已存在，可先生成硬件报告。

| 维度 | 通用结论 | 坑 |
|---|---|---|
| 显示 | 2015 年机型多为 Intel HD 4400/5500/6000 → **i915 驱动 + Mesa** 即通 | **Bay Trail / Cherry Trail 类机器为 32 位 UEFI**，64 位引导器**无法引导**，需 32 位 EFI 引导或走 BIOS 引导 |
| 网络 | 常见 Intel 网卡（`iwlwifi`）开箱可用 | **Broadcom 无线需 non-free 固件**（Debian 需加 `non-free-firmware`） |
| 输入 | PS/2 或 USB 键鼠，标准 evdev/libinput | 若走 DRM/KMS 直出，需 `libinput` 且用户加入 `input` 组 |
| 固件 | 需 `linux-firmware` | 缺固件 → 黑屏 / 无网 |
| 引导 | GPT 镜像 BIOS/EFI 均可；**Secure Boot 需签名或关闭** | 老机 BIOS 模式更稳 |
| 磁盘/内存 | 若能跑 Windows 即可跑最小 Linux | 建议 ≥2GB 内存、≥8GB 空间 |
| 图形后端 | **Vulkan 驱动未必存在**（老 Intel 走 Mesa `anv` 或退回 GL） | **必须实现 CPU 扫描输出回退**，否则老机直接黑屏 —— 这正是 `rust_embedded_wgpu` 的 fallback 的价值 |

## 四、设备三梯队评估（D5）

| 梯队 | 设备 | 判定 | 依据 |
|---|---|---|---|
| **第一梯队**（可引导 ISO 直接适配） | **2015 笔记本**、**老台式机** | ✅ **主力目标** | x86_64 标准架构；DRM/KMS 成熟；BIOS/UEFI 均可引导 |
| **第二梯队**（需额外适配） | **小米智能电视**、**先科平板**、**正方体播放器** | ⚠️ 需逐台确认 | 电视＝Android 内核（需 root/自编译或走 HDMI 输入）；平板＝ARM + **32/64 位 EFI 不确定**；播放器＝常为定制 SoC，**无公开内核/无 DRM 文档** |
| **第三梯队**（**诊断对象**，非接管目标） | **iPad 1**、**老 CD 机**、**充电宝** | ❌ **不接管** | iPad 1＝封闭引导链（无越狱不可引导）；CD 机/充电宝＝**无显示输出**，仅可作"场域诊断对象" |

> **架构含义**：第三梯队"诊断对象"与"接管目标"是**两种不同关系**——前者对应 L5 诊断层的**观察客体**，
> 后者对应 L6/L7 的**宿主目标**。建议在文档中**显式区分**，避免后续目标漂移。

## 五、⚠️ 硬约束冲突（必须先裁决）

| 冲突点 | 详情 |
|---|---|
| **C3「不用 unsafe 取巧代码」 vs DRM 直通** | wgpu 的 DRM 直通接口是 **`SurfaceTargetUnsafe::Drm { fd, plane, connector_id, width, height, refresh_rate }`**，**本身就是 `unsafe` 接口**；且需 `Instance` 带 `ALLOW_UNDERLYING_NONCOMPLIANT_ADAPTER`。**CPU 扫描回退**路径需 `drm` crate 做 ioctl，**同样 unsafe** |

**这不是"取巧"，而是"接口本身不安全"**——与 §3 里"为省事用 `transmute_copy`"性质不同。建议区分：

| 选项 | 说明 | 推荐 |
|---|---|---|
| **A. 有条件放行** | 新增 `host/field-render-kms`，在**边界处**（<50 行）集中 `unsafe`，附 `// SAFETY:` 逐条论证，**禁止 transmute**，并加 `grep unsafe` 门禁断言 | ✅ **推荐** |
| B. 用安全封装 crate | 如 `libseat`/`smithay-drm-extras` 等（仍会在内部 unsafe，但审计面转移） | 备选 |
| C. 不碰 DRM，Windows-only | 阶段二整体推迟 | 与目标冲突 |

> **建议在 `CONSTRAINTS.md` 增补 C9**：明确"unsafe 的**允许形态**"（边界集中 + SAFETY 论证 + 禁 transmute + 门禁），
> 而不是笼统禁止——否则阶段二**无法启动**。

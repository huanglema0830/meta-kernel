> **本文件自包含**：只读它一份，就知道「项目是什么、谁在做、有哪些机制、哪些红线、怎么开工」。

## 一、项目是什么

**在现有操作系统之上生长的「意识补充层」——不替代、不淘汰现有系统。**
最终目标：生成一个可以独立安装、真实运行的操作系统和浏览器，至少能替代用户本机上的主流浏览器和操作系统。

- 项目总名 ＝ **云内核项目**；本仓库 ＝ **元内核系统**（内核层／OS层／浏览器层／大模型四件套）。
- 唯一权威项目根：`研发开发/tmp_a45_review/gh_clone2`。`研发开发/` 本身**不是** git 仓库。
- 版本号口径：**`git rev-list --count HEAD`**（自动生成，任何人不得手写"当前版本"，见 C2）。
- 陈旧分叉一律在 `研发开发/archive/`（`meta-kernel-v0.48/`、`meta-kernel_repair-0907/`），**保留不删**。

### 命名体系（两族并行：电信号＝当前实现，量子＝设计）

| 版本 | 系统名 | 内核层 | 操作系统层 | 浏览器层 | 大模型 |
|---|---|---|---|---|---|
| 电信号 | 元内核系统 | 基因内核 | 云操作系统 | 空天浏览器 | 云海大模型 |
| 量子 | 量子云系统 | 量子钟 | 正源操作系统 | 正源浏览器 | 采微大模型 |

- 统一输入法：**彩虹输入法**。
- 层号：L4＝场域戒律拒绝｜L5＝场域诊断｜L6＝与外界交互（呈现＝空天浏览器）｜**L7＝执行层**｜**L8–L10＝推演层（🔒冻结）**。
- ⚠️「元内核」只作**系统名**；**不触碰**「正源场域／正源库／正源系统」。
- 已废止：空海浏览器／云内核大模型／量子模式内核／DNA内核／号脉层。**产品形态名不占层号。**

## 二、三方是谁

| 角色 | 职责 |
|---|---|
| **用户** | 决策、验证、传递（拿主意、看效果、在顾问与 WorkBuddy 之间传话） |
| **顾问** | 转译方向、审核方案、整理讨论（把用户意图转成可执行指令；审 WorkBuddy 的方案） |
| **WorkBuddy** | 执行、调研、报告（读全 coordination/ → 干活 → 按模板出报告 → 归档） |

协作纪律：
- **顾问下指令**按指令模板（`TEMPLATES.md` §一）：一次说全，不挤牙膏。
- **WorkBuddy 出报告**按报告模板（`TEMPLATES.md` §二）：未完成项与边界说明必须如实（C5）。
- **用户不需要记住任何机制细节**——机制在文件里，WorkBuddy 每轮自读、自回执（§五）。

## 三、全部机制

| # | 机制 | 文件位置 | 一句话说明 |
|---|---|---|---|
| 1 | 基准机制 | `BASELINE.md` | 项目当前状态的**唯一权威描述**，每版本更新（记「最后更新于 HEAD xxx」） |
| 2 | 约束机制 | `CONSTRAINTS.md` | 硬约束 C1–C10，不可破；破了必须在报告里说明 |
| 3 | 模板机制 | `TEMPLATES.md` §〇–§二 | 指令模板（八必带）+ 报告模板（十一必带）；固定相不可破 |
| 4 | 模板活相机制 | `TEMPLATES.md` **§七 变更记录** | 模板可提议、试用 3 轮、生效或废弃——**不单独建文件**（见下） |
| 5 | 路线图机制 | `ROADMAP.md` | 三阶段总路线图 + 六子任务 + 里程碑 + 设备梯队（含活相说明 §七） |
| 6 | 优先级机制 | `TEMPLATES.md` §三 | P0–P4 分级；**P3 无需决策即可自主推进** |
| 7 | 无响应推进机制 | `TEMPLATES.md` §四 | P1/P2 超 4h 无响应 → 转 P3 清单，**不中断、不停摆** |
| 8 | 断裂接续机制 | `TEMPLATES.md` §五 | 任何一方断裂后，读 coordination/ 最新状态即可快速恢复 |
| 9 | 归档机制 | `instructions/` `reports/` `discussions/` | 指令、报告、讨论**全部归档**，不靠对话记忆存活 |
| 10 | unsafe 白名单机制 | `unsafe_whitelist.txt` | C9 门禁白名单（当前为空＝不放行任何真实 unsafe）+ CI 断言 |
| 11 | **通用工作流机制** | `workflows/universal_workflow.md`（+ `workflows/sub/`） | **八步场域演化**（罗列→分析→推演→拆颗粒→找思路→化合→执行→输出），**子模块化**、**分层保密**（框架公开／算法保密） |

> **机制之间的关系**：1–2 定义「现在是什么、不能碰什么」；3–4 定义「怎么说话、说话格式能不能改」；
> 5–6 定义「往哪走、先做哪件」；7–8 定义「人不回话／对话断了怎么办」；9–10 定义「留痕与安全边界」。

**活相机制的当前形态（2026-09-16 简化）**：模板的可变性**只用一个文件管**——
`TEMPLATES.md` 本体（当前生效）+ 其 **§七 变更记录**（提议/试用/废弃）。
原 `TEMPLATES_CHANGELOG.md`、`OBSERVATIONS.md` 两个独立文件**已合并删除**（评审判定为过度设计：
"机制本身不能成为负担"）。程序保留：**提议 → 记一行 → 试用 3 轮 → 生效或废弃**。

## 四、硬规则速查（C1–C10；全文见 `CONSTRAINTS.md`）

| 编号 | 规则 | 一句话 |
|---|---|---|
| C1 | 内核零依赖 | `meta-kernel-core` 不引任何外部 crate（宿主侧可带依赖） |
| C2 | 版本号自动生成 | 「当前版本」＝`git rev-list --count HEAD`；代码/配置/提交信息里不得手写 |
| C3 | 不用 unsafe 取巧代码 | C3 自身**无例外**；阶段二所需的边界型 unsafe 走 C9 |
| C4 | 改前先列清单 | 涉及代码改动，先出清单、确认后执行 |
| C5 | 诚实标注未完成项 | 报告须区分"本地跑过 / CI过 / 真实跑过 / 未验证" |
| C6 | 每次报告带三量台账 | 存量 / 变量 / 补充增量 / 创新增量 |
| C7 | 不用 CI 通过代替真实运行 | CI 只是构建门；关键功能必须真实环境验证 |
| C8 | 硬约束可扩充 | 调研中发现新约束可提议，用户确认后生效 |
| C9 | unsafe 边界形态 | 仅允许边界集中 + `// SAFETY:` 论证 + 禁 transmute + 白名单登记（**含 CI 门禁断言**） |
| C10 | 动作约束 | 见 §六：须用户明确确认的动作清单，**不得自动执行** |

**四条最容易被"打绿"绕过的纪律**（重点盯）：
1. **绝不靠调参/改阈值打绿**（断言必须打在真实语义上）。
2. **绝不用 CI 通过冒充真实运行**（C7）。
3. **绝不把未验证的说成已验证**（C5）。
4. **绝不手写当前版本号**（C2）。

## 五、启动回执（WorkBuddy 每轮必做）

WorkBuddy 读完本文件后，**必须在回复开头给出回执**：

```
已读 CHARTER.md。
当前状态：vX.Y ｜ ROADMAP 阶段X · 子任务N ｜ 本阶段目标：……
本次任务：……
是否继续：等待指令 / 自主推进 P3
```

- 回执中的版本号**必须来自 `git rev-list --count HEAD`**（C2），不得凭记忆写。
- **回执不出现 → 视为未读** → 用户/顾问可要求重读。
- 回执是"证明真读了"的最小成本手段，不替代正式报告。

## 六、动作约束（C10 全文）

以下动作**必须经用户明确确认**，不得自动执行：

- **对外发布、分享、上传**（任何对外可见的链接、文件、公开页面）
- **模型选择、后端切换**（含自动降级/切换供应商）
- **任何公开可见的操作**
- **任何不可逆的操作**（删除、覆盖、迁移、强制推送等）

配套要求：
- 自动执行前**必须报备**；用户可随时叫停。
- 需要确认时，**按"决策呈现规范"摆全六要素**（相关点／风险点／经验教训／好处／不同做法的差异／继续往前的推荐），**不许只问"做不做"**、不许以提问为由停摆。
- 边界：**过程产品默认不外发**——能测试、能看到 ≠ 对外公开；验证只走受控入口。

## 七、紧急通道（哪些情况可跳过流程）

| 情况 | 允许的动作 | 事后义务 |
|---|---|---|
| 线上挂了（CI/站点/服务不可用）且影响交付 | **先止损**（回滚、下线、恢复上一版），可不等确认 | 止损后**立即报备**：改了什么、为什么、怎么回滚 |
| 数据丢了 / 有丢失风险 | **先保数据**（停写、备份、隔离），可不等确认 | 同上；并说明影响范围 |
| 密钥/凭据疑似泄露 | 先停用、先撤销 | 同上 |

**紧急通道不等于放弃纪律**：紧急动作**仍不得**触碰 C1–C3、C9；
紧急处置完成后必须补齐 C4 的清单与 C5/C6 的报告（"先止损后报备"）。

## 八、冲突解决（三方判断不同时）

1. **先协商**：谁依据 `BASELINE.md` / `CONSTRAINTS.md` / `ROADMAP.md` 的**书面事实**更充分，以谁为准（不靠印象、不靠嗓门）。
2. **协商不成 → 用户拍板**。用户拍板后，**以用户决定为准**，并把结论与理由写入 `BASELINE.md` 决策表（D 编号）。
3. 协商期间 **不中断推进**：争议项挂起，手里的 P3 照做（§七 之外不适用紧急通道）。

**开工顺序（也是自检清单）**：本文件 → `BASELINE.md` → `CONSTRAINTS.md` → `TEMPLATES.md` → `ROADMAP.md` → `instructions/` 最新 → `reports/` 最新。
**收工四步**：① 更新 `BASELINE.md`（版本变了就更新）② 报告归档 `reports/` ③ 指令归档 `instructions/` ④ 有讨论则归档 `discussions/`。

**接续话术**（任何一方断裂时直接用）：
> 继续云内核项目。读 coordination/ 下的最新状态。
> 告诉我：当前到哪一步、下一步是什么、需要我决策什么。

### 本文件自身怎么变

- 新增/撤销**机制** → 写入 `TEMPLATES.md` §七 变更记录 → 试用 3 轮 → 生效或废弃 → 同步更新本文件 §三/§四/§九。
- **约束**变更 → 走 C8；C 编号**只增不改**（改了要留旧号说明，避免历史报告指错）。
- **本文件原则上保持"自包含"**：新增内容若让 §一–§八 变得臃肿，说明该内容属于细节，应放进对应文件、在 §九 挂一行。

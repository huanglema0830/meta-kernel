# 接口 ②：降级规则（**骨架**｜🔒 半公开）

> **本文件只写「做什么」。** **降级链的具体顺序、额度阈值、触发条件**见实现层：
> `{PRIVATE_ASSETS}/llm/02_degradation_impl.md`
> 归口：**机制 17 拆分机制**｜保密级别：🔒 半公开（C12）

## 一、职责（做什么）

当**上游档位不可用**时，把请求**往下降**到下一个可用档，并**如实告知**调用方。
"不可用"的典型来源（**只说类别，不说阈值**）：

| 类别 | 说明 |
|---|---|
| **额度耗尽** | 某档的**免费额度**／预算已用尽 |
| **限流** | 被上游限流、需等待 |
| **故障** | 上游报错或超时 |
| **主动收缩** | 本次任务被判定为"不值得用高档"（成本治理） |

## 二、接口（形态）

```
输入  Grade（来自接口 ①）+ 可用性状态（哪几档当前可用）
输出  Result {
        chosen:     实际使用的档
        degraded:   是否发生了降级（bool）
        chain:      本次**走过的**降级路径（用于审计与告知）
        reason:     降级原因（可复述给用户）
      }
```

## 三、四条硬规则（**这是本接口的实质，必须可测**）

| 规则 | 内容 | 为什么 |
|---|---|---|
| **① 单向** | 只能**往下降**（复杂→中等→简单），**永不自动升档** | 自动升档＝**成本失控**且**不可预期**；升档必须是**人的决定** |
| **② 有底** | 降到**最低档**仍不可用 ⇒ 返回**明确失败**，**不得**无限重试、**不得**静默跳过 | 静默跳过 = **用户以为做了、其实没做**（最坏的一类错） |
| **③ 必告知** | **只要 `degraded = true`，就必须把 `chain` 与 `reason` 回给调用方**，并进接口 ③ 的账 | 降级若不被看见，**质量下降会被误读成模型变差** |
| **④ 必记账** | **每一次**降级都留一条账（含"本可用的档"与"实际用的档"） | 否则**无法回答"这个月因为额度损失了多少质量"** |

> ⚠️ **本接口刻意不写"降级链长什么样"** —— 那是实现层。本文件只固定**不变量**（单向／有底／必告知／必记账）。

## 四、边界（**不做什么**）

| 不做 | 为什么 |
|---|---|
| **不自动升档** | 见规则 ① |
| **不静默重试** | 重试次数与退避策略属实现层，且**必须留痕** |
| **不替用户决定"降级后还做不做"** | 降级只回答"用哪档"；**"做不做"由调用方/用户定** |
| **不在此文件写价格与额度** | ⛔（实现层） |

## 五、验收（可判定）

| 标准 | 判据 |
|---|---|
| **单调不升** | 构造"高档不可用"场景，实际档位**必须 ≤ 起点档**；**永不出现升档**（可测） |
| **有底不空转** | 全档不可用时返回**失败**（非重试、非空成功） |
| **降级必可见** | `degraded=true` ⇒ `chain` 与 `reason` **均非空** |
| **降级必留账** | 每次降级在接口 ③ 的账里**恰好一条**记录 |

## C1：内核零依赖

- **为什么**：保持内核纯净、可审计、可移植
- **破了会怎样**：依赖链膨胀，wasm体积增大，审计困难
- **适用范围**：meta-kernel-core
- **例外**：宿主侧可带依赖（wgpu/egui/web-sys等）
- **⚠️ 界线举例（2026-09-17 用户确认，D34-b）**：
  - ✅ **`core` / `alloc` 属 Rust 标准分发**，**不算外部依赖**（随 `rustup target` 一起提供，**不进 Cargo.lock 的第三方段**）
  - ❌ **第三方 crate**（如 `heapless`、`libm`、`spin` 等）**算外部依赖**，内核侧一律不得引入
  - ⚠️ **用 `alloc` 不等于放开 unsafe**：`alloc` 的**使用**（`Vec`/`String`）是安全 API；
    但**提供** `alloc` 所需的 `GlobalAlloc` 实现**受 C9 约束**（须走白名单 + `// SAFETY:` + 禁 transmute）
  - ⚠️ **`alloc` 使用不得引入外部 crate**（例：不得为了"方便"引入 `hashbrown` 来换掉 `HashMap`）

## C2：版本号自动生成，不手写

- **为什么**：避免"手写vs自动"不一致
- **破了会怎样**：版本号混乱，无法追溯
- **规则**：`git rev-list --count HEAD`——**「当前版本」永远以此为准**
- **禁止**：在**代码 / 构建配置 / 提交信息**中出现手写版本号
- **允许（且鼓励）**：**文档**中记录「最后更新于 HEAD xxx（对应 vX.Y）」。
  这是**「更新时的版本快照」**，用于溯源自何时、非当前版本；文档内容会随提交自然滞后，属正常现象，不视为违反 C2。
- **判据**：读到一个版本号时，先问"它说的是**当前**还是**更新时**"——前者必须来自 `rev-list`，后者必须标明是快照。

## C3：不用unsafe取巧代码

- **为什么**：不留隐患，保证安全
- **破了会怎样**：潜在内存安全问题，难以调试
- **例外**：**无**（阶段二 DRM/KMS 所需的边界型 unsafe **不由 C3 放行**，见 **C9**）
- **要求**：`grep -rn "unsafe" src/` 结果必须全在注释里
- **判据**：**"取巧"**＝为绕过类型/生命周期约束而用 unsafe 抄近路；**"边界"**＝不得不穿越 FFI/系统接口的那一小段。前者永远禁止，后者按 **C9** 合规放行。

## C4：改前先列清单，确认后执行

- **为什么**：避免误改、误删
- **破了会怎样**：不可逆损失
- **要求**：涉及代码改动时，先出改动清单，用户确认后执行

## C5：诚实标注未完成项

- **为什么**：避免"声称完成实际没完成"
- **破了会怎样**：信息失真，决策失误
- **要求**：报告必须区分"本地跑过/CI过/真实跑过/未验证"

## C6：每次报告带三量台账

- **为什么**：保证信息完整，可追溯
- **破了会怎样**：信息丢失，无法复盘
- **要求**：存量/变量/补充增量/创新增量

## C7：不用CI通过代替真实运行

- **为什么**：CI通过≠真实能跑
- **破了会怎样**：核心目标（能看网页）从未被验证
- **要求**：关键功能必须在真实环境验证，CI只是构建门

## C8：硬约束本身可扩充

- **为什么**：项目在演化，约束会新增
- **要求**：WorkBuddy调研时发现新约束，可提议加入，用户确认后生效

## C9：unsafe 只允许"边界形态"，不允许"取巧形态"

- **为什么**：阶段二（可引导 ISO）走**裸机 DRM/KMS** 输出——wgpu 的
  `SurfaceTargetUnsafe::Drm`、以及 CPU 扫描输出回退所需的 `drm` ioctl，**本身就是 unsafe 接口**。
  若不给出合规形态，C3（不用 unsafe 取巧代码）就会被"要么破规矩、要么做不了"的僵局顶死。
  本约束的作用是**把 unsafe 关进笼子**，而不是放开它。
- **破了会怎样**：unsafe 从"一小段边界"扩散到业务逻辑 → 内存安全隐患、审计失效、C3 形同废止。
- **适用范围**：全仓库（内核 `meta-kernel-core` + 宿主 `host/*`）。
  ⚠️ **内核零依赖红线（C1）不因 C9 松动**——内核侧原则上仍应做到 unsafe = 0。
- **允许形态（四条同时满足才算合规）**：
  1. **边界集中**：unsafe 只能出现在**专门的边界模块**（如 `host/field-render/src/drm_ffi.rs`），
     **不得散落在业务逻辑**；对外暴露 `safe fn`，把 unsafe 封闭在模块内部。
  2. **`// SAFETY:` 论证**：每一处 `unsafe` 块**必须**紧跟 `// SAFETY:` 注释，写清"为什么此处成立"
     （前置条件、由谁保证、失效会怎样）。没有论证 = 违规。
  3. **禁 `transmute`**：`std::mem::transmute` **一律禁止**（含其别名/重导出）；
     需要类型转换时用显式字段重解释或 `#[repr(C)]` + 逐字段转换。
  4. **门禁断言**：CI/本地门禁必须能自动判定——
     ```bash
     # ① 全仓 unsafe 出现位置必须落在白名单文件内
     grep -rn "unsafe" --include="*.rs" meta-kernel-core/src host/*/src | grep -vE "^\S+:\s*//" > unsafe_hits.txt
     # ② 白名单：coordination/unsafe_whitelist.txt（一行一个相对路径；无条目=不允许任何真实 unsafe）
     # ③ transmute 绝对禁止
     ! grep -rn "transmute" --include="*.rs" meta-kernel-core/src host/*/src
     ```
     断言规则：**白名单外的任何真实 unsafe（非注释）都算违规，CI 必须红**。
- **现状（诚实标注）**：真实 unsafe **0 处**（`unsafe_whitelist.txt` 目前为空），
  即"白名单机制已就位、尚未放行任何条目"。阶段二落地 DRM/KMS 时，**按需逐条申请**、
  在 `unsafe_whitelist.txt` 登记并附 `// SAFETY:` 论证，经确认后再放行。
- **判据**：读到一个 `unsafe`，先问三句——① 它在不在边界模块里？② 它头上有没有 `// SAFETY:`？
  ③ 白名单里有没有登记？**三问有一问不过，就是违规。**
- **门禁落地（D11/R10，2026-09-16）**：上述四条已由 CI `host-windows` 的
  **验收⑤「C9 门禁」** 自动判定——① `transmute` 零出现（词边界匹配）② 真实 unsafe 所在文件必须全在白名单
  ③ 每个文件的 `// SAFETY:` 次数 ≥ 真实 unsafe 处数 ④ **门禁自检**（正反两侧样例，防断言空转）。
  判据锚在**关键字/调用的确切用法**上：`unsafe_q` 这类**变量名**、`#[allow(unsafe_code)]` 这类**属性**，
  以及注释里提到的关键字，**均不算违规**（门禁第一次干跑正是误报 `unsafe_q` —— 真实缺陷，已修并固化为回归样例）。

## C10：动作约束（以下动作必须用户明确确认，不得自动执行）

- **为什么**：用户明确关心过的动作（对外发布、分享、上传、模型/后端切换）若被"自动顺手做掉"，
  后果往往**不可逆**且**已对外可见**，事后无法收回；且这类动作会动摇"过程产品不外发"的既定边界。
- **破了会怎样**：过程版本被当成成品外发；用户还没看过的东西已经公开；模型/后端被悄悄切换导致结论不可复现。
- **须确认的动作清单**：
  1. **对外发布、分享、上传**（任何对外可见的链接、文件、公开页面）；
  2. **模型选择、后端切换**（含自动降级、自动换供应商）；
  3. **任何公开可见的操作**；
  4. **任何不可逆的操作**（删除、覆盖、迁移、强制推送等）。
- **配套要求**：
  - 自动执行前**必须报备**；用户可随时叫停。
  - 需要确认时按**「决策呈现规范」摆全六要素**（相关点／风险点／经验教训／好处／不同做法的差异／继续往前的推荐），
    **不许只问"做不做"**，**不许以提问为由停摆**（手里的 P3 照做）。
  - 边界重申：**过程产品默认不外发**——"能测试、能看到" ≠ "对外公开"；验证只走受控入口。
- **判据**：动手前问一句——**"这件事做完，外面有人能看见吗？能撤回吗？"**
  只要有一问是"是/不能"，就必须先确认。

## C11：决策评估机制

- **为什么**：确保顾问提供完整信息，用户做决策
- **破了会怎样**：顾问越权决策，用户失去控制
- **要求**：
  - 凡涉及决策，顾问必须给**七要素**（**评估／优势／劣势／风险／机会／建议／等待决策**）
  - 用户决策前，顾问**不得擅自执行**
  - 决策后，WorkBuddy 按用户决策执行
- **适用范围**：**顾问侧**（不是 WorkBuddy 侧）
- **配套**：
  - 顾问侧格式见 `TEMPLATES.md` §九「决策评估模板」；选项多于 2 个时**必须**附"各选项对比"表。
  - 优势/劣势/风险各**至少 2 条**，且"具体到可验证"；风险需**标注概率与影响**。
  - **机会**至少 1 条，且必须是**可被验证或否证的方向**（不许写"可能有更大价值"这类空话）。

### 「优势」与「机会」的区别（新增第七要素的理由）

| | **优势** | **机会** |
|---|---|---|
| **确定性** | **确定的**（做这件事本身的好处） | **可能的**（做这件事可能带来的额外可能性） |
| **可验证性** | **可当场/事后核验**（有数字、有退出码、有产物） | **可被证伪的方向**（须写清"什么情况算没兑现"） |
| **失败形态** | 只要做了就一定拿到 | **可能不兑现**；不兑现≠决策错误（但须能被追溯） |
| **典型写法** | "路径 A 每步可独立验证（`cargo build` 成功即达成）" | "阈值来源抽象可**复用到 2.4/2.5** 的 ACPI 读入" |
| **反面写法（禁止）** | "更稳、更好" | "可能价值更大"（无证伪条件） |

> **为什么非要拆开**：把"机会"混进"优势"会**虚增确定性** —— 用户会以为那些附加可能性**已经到手**，
> 于是在"优势 3 条 vs 劣势 3 条"的错觉里拍板。拆开后，用户能看清：
> **确定拿到的有哪些、只是"可能"的又有哪些**，再决定这份"可能性"值不值得为之承担风险。
> 这直接服务于本机制的目的——**信息完整，用户做决策**。

- **与跨项目「决策呈现规范」的关系（避免混淆）**：
  | 场景 | 用哪套要素 |
  |---|---|
  | **顾问 → 用户**（本条 C11） | **七要素**：评估／优势／劣势／风险／**机会**／建议／等待决策 |
  | **WorkBuddy → 用户**（用户跨项目规范） | 六要素：相关点全列／风险点（含不做的风险）／经验教训／好处／不同做法差异／继续往前的推荐 |
  > 口径说明（诚实标注）：WorkBuddy 侧那套六要素中的「**好处**」**本身已含"确定的＋可能的"两层**（其原文本就要求"收益，尽量可衡量"），
  > 故**顾问侧拆出"机会"后，两侧不构成冲突**，只是**颗粒度不同**——顾问侧更细。两套**并存、各自适用**。
  共同底线相同：**不许只问"做不做"、不许把决策裸推、不许以提问为由停摆**。

## C12：保密机制

- **为什么**：防止机密信息泄露
- **破了会怎样**：密钥泄露、账号被盗、内部信息外流 ｜**密钥级别：⛔ 机密**（本体／路径／其余一律先按机密）
- **要求**：
  - WorkBuddy **报告时必须标注保密级别**
  - **机密信息不得出现在拷给顾问的内容中**
  - 顾问如发现机密信息，**必须提示用户**
  - **双方都有提示义务**
- **适用范围**：**三方共用**（用户／WorkBuddy／顾问）

### 四级别（标记与口径）

| 级别 | 标记 | 含义 | 拷给顾问时 |
|---|---|---|---|
| 公开 | 🔓 | 框架、思想、术语 | **直接拷** |
| 半公开 | 🔒 | 映射关系、部分实现 | **可拷**，顾问应知悉 |
| 保密 | 🔐 | 算法公式、阈值、权重 | **屏蔽后拷** |
| 机密 | ⛔ | 密钥、账号、具体路径、网络细节 | **绝不拷** |

### 机密清单（⛔ 绝不拷给顾问）

1. **密钥 / token**：SSH 私钥、API token、登录密钥 ｜**密钥级别：⛔ 机密**（本体／路径／其余一律先按机密）
2. **账号**：邮箱、手机号、用户名
3. **具体路径**：`C:\Users\...` 一类本机绝对路径
4. **网络细节**：内网 IP、DNS、代理配置
5. **服务器地址**：具体域名、端口
6. **参数库内容**：具体公式、阈值、权重

### 报告中的落地格式（配合 `TEMPLATES.md` §二）

```markdown
【保密标记】
⛔ 机密（绝不拷）：[清单]
🔐 保密（屏蔽后拷）：[清单]
🔒 半公开（可拷）：[清单]
🔓 公开（直接拷）：[其余]
【给用户的提示】本次报告包含 X 处机密、Y 处保密。拷给顾问时，请屏蔽 ⛔ 部分。
```

- **判据**：报告里凡出现 **`C:\` 路径、`ssh-`/`token`/`key`/密码字样、IP/端口数字**的一律先按 ⛔ 处理，再逐条判断是否可降级。
- **注**：**分级"宽严"由用户定**——把某条降级或升级，属**用户决策**（C11），不由执行方自行放宽。

## C13：顾问阅读指令

## C15：编号表编辑纪律（**编辑前后双向计数**）

- **为什么**：本项目**已复发 5 次**同一类失误——**往编号表"追加一行"，结果把既有行替换掉**
  （误替换 R18→R19｜误删 D23/D24｜重复插入 D19｜误把机制 16 替换成机制 17｜**误删 `BASELINE.md` 的 D33 行**）。
  根因在**编辑动作本身**（`old_string` 只取了既有行的一部分、`new_string` 未把既有行带回），**不是"记性不好"**
  ⇒ 只能靠**机械判据**兜住。
- **破了会怎样**：**编号表静默丢行**。被删的那条**在 git diff 里混在大段改动中**，肉眼极易放过；
  而编号表承载的是**风险 / 决策 / 机制**的权威记录，丢一条 ＝ **某条风险或决策无声消失**
  —— 比"直接报错"危险得多。
- **要求**（**三段式，缺一不可**）：
  1. **编辑前取数**：先 `grep -c "^| <行首标记>"` 记下**编辑前**条数
     （例：`grep -c "^| \*\*D" coordination/BASELINE.md`）；
  2. **编辑后复算**：改完**立刻**用**同一条命令**再取一次；
  3. **差值必须与预期一致**：**加 1 条 ⇒ +1**｜**改 1 条 ⇒ ±0**｜**删 1 条 ⇒ −1**。
     **不符即视为丢了内容，立即定位并修复**（不得"看看没问题"就放过）。
  > **附**：**编号连续性**也是判据（`R1..R24`／`D1..D34-b`／`C1..C15`／`T-001..T-018`／机制 `1..19`
  > 应**无缺号、无重复**）—— 连续性比"看起来对"可靠得多。
- **适用范围**：**三方共用**（凡编辑 `BASELINE.md`／`CHARTER.md`／`CONSTRAINTS.md`／`TEMPLATES.md`／`ROADMAP.md`
  中的**任何编号表**）
- **判据**：回答四问——「**这次是加、是改，还是删？预期差值是几？实测差值是几？编号还连续吗？**」
  四问答不全，就不算执行过本条。
- **与 `TEMPLATES.md` §〇「表格编辑纪律 R-a..R-d」的关系**：本条＝把其中的 **R-b 升格为硬约束**，
  并**补上"编辑前"一侧**（原 R-b **只要求"编辑后复核"、缺"编辑前基线"**
  ⇒ 只能判断"看起来对不对"，**判断不了"少了没有"**）。

## C16：断言「不存在」须给四要素

- **为什么**：**v0.194 一轮查证推翻了 v0.193 的 3 条结论**（τ「全库无定义」／「L7 被卡」／L0-V1「自相矛盾」），
  三条**同根**——**只在 1 份文件里检索过，就下了"全库"结论**。
  例：τ 其实在 `FIELD_REPAIR_DESIGN.md` 行27–35 有完整七维表、`L5_VALIDATION_REPORT.md` 行93–95 有实测值 6.587，
  我只是**没翻到那两份**就写成"底图里没有"。
- **破了会怎样**：**误判底图 ⇒ 按误判去改底图 ⇒ 底图被自己的猜测污染**。
  发起人 2026-09-18 的批评——「你给我的全量汇编当中，有好多是你自己加上去的」——**正是这一类**。
  比"报错"危险得多：报错会被拦下，**误判会一路走到改文件**。
- **要求**（**四要素，缺一不可**）：

  | # | 要素 | 具体要求 |
  |---|---|---|
  | ① | **检索式** | 给出**实际使用的字面串或正则**，不得只写"我查了" |
  | ② | **检索范围** | 哪个目录／哪些文件／**共几份**；是否含代码、是否含 `archive/`、**是否含仓库外** |
  | ③ | **命中数** | 逐条给**数字**（0 也是数字），不得只写"没有" |
  | ④ | **阳性对照** | 用一个**已知确实存在**的同族对象跑**同一条检索式**，**必须命中**。<br>阳性对照不命中 ⇒ 检索式或范围本身有问题 ⇒ 结论无效 |

  > **四缺一 ⇒ 只能写「未检索到」，不得写「不存在」／「全库无」／「从未」。**
- **适用范围**：**三方共用**。凡对**底图／代码／台账**下「不存在」「全库无」「从未」「没有定义」类断言，一律适用。
- **判据**：回答四问——「**检索式是什么？范围几份？命中几？阳性对照命中几？**」
  四问答不全，就不算执行过本条。
- **示范（本轮 v0.196 已按此执行）**：查「`/v1/msg|report|alerts|tasks` 在底图有无定义」——
  ① 检索式：字面 7 个路径 ② 范围：`docs/*.md` 全 35 份（另跑仓库递归 112 份）
  ③ 命中数：**全部 0 份** ④ 阳性对照：`/v1/probe` 用同一检索式命中 **6 份** ⇒ 检索式有效 ⇒ **"底图无定义"成立**。
  **若没有第 ④ 步，这个"0 份"与上一轮的 τ 误判无法区分。**

## C19：同一机器事实，只许有一份口径实现（判据↔判据同源）

- **为什么**：**R79（2026-09-19 实测事故）** —— **同一机器事实（"源模块集是否已被目标覆盖"）被两个判据各算一遍**：
  `check_migration_closure.py` 用**递归** `os.walk`（源 **56**），`check_doc_consistency.py` 用**顶层** `glob("*.rs")`（源 **47**）
  ⇒ **同一个仓库状态，两个判据报出两个数**，并给出**看似相反**的结论
  （closure 报 **PASS**、机制 25 报 **「未收口（剩余 1）」**）。
  ⇒ 根因有三层：① **枚举口径不一致**（差 **9** 个模块：漏 `l4/*`＋`l7/*` 共 8 个 ＋ `lib` 归一）；
  ② **术语混用**（closure 的 `PASS` 是**「封闭性」**，**不是「已收口」**）；③ 机制 25 的 P2 只做了**单侧**检查。
- **破了会怎样**：**二义性** —— 两个都"有判据支撑"的结论互相矛盾时，**无法用机器判定谁对**，
  只能靠人工裁决 ⇒ 判据从"地基"退化为"另一个需要被质疑的说法"。
- **要求**（**三条，缺一不可**）：

  | # | 要求 | 具体做法 |
  |---|---|---|
  | ① | **单一实现** | 同一机器事实的**枚举／计数／解析**只允许**存在一份实现**；其余判据**直接 `import` 复用**该实现（**禁止各写一份**） |
  | ② | **口径写进输出** | 判据的**运行输出**必须显式打印其**口径来源**（如「枚举口径：与 `check_migration_closure.py` 同源」），使读者能**当场核对**两个判据是否同源 |
  | ③ | **概念分离** | **一个 `PASS` 只能代表一件事**：把"封闭性"与"收口"这类**相邻但不同**的概念**分行输出**，并显式注明「本 PASS 不覆盖 X」 |

## C20：CI 结论不入库（**治 R82 自指递归**）

- **底线**：**「本轮 CI 的结论」不入仓库**。CI 的三 job 状态、run 号、job 用时等
  **只写进项目日报（`.workbuddy/memory/YYYY-MM-DD.md`）**，**不写进任何跟踪文件**。

- **为什么**（**R82 自指递归**，本轮的推理链）：
  提交 → 触发 CI → 把 CI 结论写进仓库 → **产生新提交** → **再触发 CI** → 结论又变了 → ……
  ⇒ **没有不动点**。上一轮（v0.236／v0.238）已连着两次为"补记 CI 结论"单独提交，
  **每补一次就再生一个待补的 CI** ⇒ 这是**结构性的**，不是"多写一行"的问题。
  边角证据：`BASELINE §二十` 曾写「CI 结论见 §二十一」而 §二十一**当时并不存在**
  ⇒ 同一个病（**"将要在别处记录"而别处未建**）的另一种形态。

- **要求**（**三条，缺一不可**）：

  | # | 要求 | 具体做法 |
  |---|---|---|
  | ① | **只记日报** | CI 结论（run 号／job 三态／关键标记）写**日报**；仓库侧**只留"复核命令"** |
  | ② | **仓库侧只引命令** | 需在仓库里提到验收状态时，写**命令**（`gh run list --limit 3`／`gh run view <id> --json jobs`）＋**取数时点**，**不写死 run 号与结论**（R71 同源） |
  | ③ | **代码提交即终态** | 一次推送**只为一个"代码／文档事实"**服务；**不为"记录 CI 结果"再推一次** |

- **适用范围**：**一切会因提交而变化的观测值**（CI 状态、run 号、制品 ID、部署哈希…）。
  ⚠️ **不适用**于"**代码本身的判据**"（测试计数、模块数等仍按 R71 引命令）。

- **判据**：三问——「**这条结论会不会因为我又提交一次而变？** 会 ⇒ 它就该在日报，不在仓库。」
  「**仓库里写的是命令，还是写死了 run 号／结论？** 写死了 ⇒ 违反 C20。」
  「**这次推送是不是只为记录上次 CI？** 是 ⇒ 违反 C20。」

- **与既有条目的关系**：
  - **R71**（环境派生值不抄进文档）**管"怎么引"**，**C20 管"该不该入库"** ⇒ **上下位**关系；
  - **R82**（数值型活跃陈述会静默过期）**是病象**，**C20 是该病象在"CI 结论"这一类上的处置**；
  - **与 C13／机制 18 不冲突**：阅读指令（第 0 行）**属模板抽取**，不是 CI 观测值。

## C21：版本号口径唯一（`label = count`；**前缀不改变版本号**）

- **底线**：**版本号 = `git rev-list --count HEAD`**。**一次提交一个号，不区分提交类型**；
  **`夜间 P3-n：` 前缀（机制 23）只用于区分来源，不改变版本号**。

- **为什么**（**R84 · 2026-09-20 查明**）：
  自 count 230 起，本仓库版本号**一致偏移 −5**（`label = count − 5`，持续 14 条）。
  逐条取证（全量 **246** 条提交）后定位根因：**count 225–229 的 5 条「夜间 P3」提交被排除出版本计数**。
  - **排除无成文依据**：底图 `README.md` **行 90**（版本号 = 提交计数）＋**行 93**（**一律以提交计数为准、不再人为指定**）／
    `CONSTRAINTS.md` **C2**／`CHARTER.md` 行 34・126・145・160 —— **四处一致要求 `label = count`**；
    而 **机制 23** 只规定用 commit 前缀**区分来源**，**从未**规定"夜间提交不计版本号"。
  - ★ **排除法自身不成立**：**同一类事实（夜间 P3 提交）三处处理不同** ——
    count **187–190**（4 条）**未排除**（191 = v0.191）｜count **204–206**（3 条）**未排除**（207 = v0.207）｜
    count **225–229**（5 条）**被排除**（230 = v0.225）。⇒ **它是个案，不是规则**。
  - ★ **机器否证**：对全量提交做**四规则假设检验**（「offset 恒 0」**70/93**｜「排除全部无 v 标签」**1/93**｜
    「排除全部夜间 P3」**39/93**｜「只排除紧邻无标签」**69/93**）⇒ **四条全部被反例否证**；**不存在**能复现实测序列的规则。
  - **漂移的思想来源**：底图 `README.md` **行 89** 原写「每次**实质性**迭代（代码提交／模块交付／验收通过）累加 1」，
    与行 90「= 提交计数」**存在张力**（"非实质性提交"算不算无解）⇒ **2026-09-20 该行已修订为「每次提交累加 1（不区分提交类型）」**
    （修订前后逐字对照见 `BASELINE.md`）。

- **破了会怎样**：**版本号不可复现** —— 同一提交出现两个"应该的"版本号（一个按 count、一个按"排除后"），
  报告／`BASELINE`／`ROADMAP` 三处引用口径不一 ⇒ 属 **C19 家族**（同一事实两份口径）。
  更危险的是**口子一开就没有边界**：任何"我觉得不实质"的提交都可被排除 ⇒ 版本号退化为**主观标记**（违反 C2"自动生成"的本意）。

- **要求**（**三条，缺一不可**）：

  | # | 要求 | 具体做法 |
  |---|---|---|
  | ① | **唯一取数** | 版本号**只**取 `git rev-list --count HEAD`；提交信息中的 label 取**该提交落地后的实时值**；**禁止任何"排除某类提交"的推算**（含 −N 偏移、"跳过夜间"、"只出稿不算"等） |
  | ② | **前缀不派生版本号** | `夜间 P3-n：`（自动化任务）与 `v0.xxx`（用户在场会话）是**两种 commit 前缀**，只用于**区分来源**（机制 23）；**两者互不派生** —— 带 `夜间 P3-n：` 前缀的提交**同样计入版本号** |
  | ③ | **可复现判据** | 读到任一 label ⇒ 必须能用 `git rev-list --count <该提交>` **复现**（`label == count`）；**不能复现 ⇒ 判红**。**历史例外**（旧人工口径 `v0.001`／`v0.002` 段、count **115**、count **230–246**）**只作历史事实登记，不回改**（改写已推送历史属破坏性操作） |

- **适用范围**：**三方共用**（凡写／读／引用版本号处）。

- **判据（三问）**：「**这个号是取出来的，还是推出来的？**推出来 ⇒ 违反本约束。」
  「**它能不能用 `git rev-list --count <该提交>` 复现？**不能 ⇒ 违反本约束。」
  「**有没有以"非实质性""夜间""只出稿"为由排除某次提交？**有 ⇒ 违反本约束。」

  - **C2 管"不得手写"**（来源必须自动）；**C21 管"不得推算／排除"**（取数口径唯一）—— **互补**，同属"版本号可信"。

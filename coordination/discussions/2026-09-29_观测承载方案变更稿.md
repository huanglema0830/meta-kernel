# 观测承载方案变更稿 —— 「单次执行 + 平台定时触发」（`云内核-C3-031` §二）

> **指令来源**：用户 2026-09-28／29 `云内核-C3-031` §二（P0）；用户裁定「**改为"单次执行 + 平台定时触发"方案**」。
> **依据**：`T-127`（1 小时窗口被回收）／`T-116`（宿主承载）／`T-111`（探针形态）／§二十四 24.4（红线）／机制 32。
> **不做什么**：**本稿不创建任何平台定时任务**（触机制 32 ⇒ 须用户明示，§2.4-2）；**不改内核代码**（守禁区⑦／⑪）。

---

## 一、变更缘由（一句话 + 实证）

★ **一句话**：**进程承载不住「≥1h 的观测」** —— 心跳此前依赖"进程还在跑"，而进程**不跨 agent 轮次存续**。

| # | 实证 | 结果 |
|---|---|---|
| 1 | `nohup … &`（detached） | ★ **只写 `seq=1`** 即被终止（`T-119`，两次复现） |
| 2 | **harness 后台任务** | ★ **存活 ≈ 33 分钟**（≈ 单轮时长）⇒ `B1` 仅 **33/60**，**无收尾件 `summary.json`**（`T-127`） |
| 3 | ★★ **本轮第三次复现** | ★ 用 `nohup` 起循环脚本（60 次 × 3s 与 60 次 × 60s 两窗口）⇒ **两窗口均仅 tick 1 次即停** |

⇒ ★ **结论**：**问题不在"间隔设多长"，而在"靠一个长命进程"这个形本身**。

---

## 二、新方案（形）

> ★ **进程短跑，状态长活**；**心跳不再依赖"进程存活"，而依赖"状态文件在推进"**。

```
平台定时任务（每 60 s 触发一次）
        │  每次触发 = 一个**独立短进程**
        ▼
  载-甲 tick（launch_tick.sh）  ──►  宿主（--once）
        │                                 │
        │                                 ├─ ① 读 snapshot.json（不存在⇒首次）
        │                                 ├─ ② 重放账本 1..seq（纯函数 ⇒ 完全确定）
        │                                 ├─ ③ append 一条（seq+1）
        │                                 ├─ ④ 写回 snapshot.json（双件原子）
        │                                 ├─ ⑤ 追加一行 readings.csv
        │                                 └─ ⑥ 退出
        ▼
   观测方：读 readings.csv / snapshot.json ⇒ 看**时间戳是否推进**
```

## 三、★ 宿主改造前后对照

| 维度 | **改造前**（循环形） | **改造后**（单次形） |
|---|---|---|
| **入口** | `--interval N --cycles M`（循环 M 次） | ★ 新增 `--once`（**一次调用 = 一个周期**） |
| **进程寿命** | 一个进程跑满 M 个周期（**≈ M×N 秒**） | ★ **每次 ≈ 0.55 s**（实测） |
| **状态载体** | **进程内存**（`ActionLedger` 实例 ＋ `prev_snap_ts` 变量） | ★ **磁盘 `snapshot.json`**（`seq` ／ `prev_snap_ts` ／ `last_head`） |
| **账本恢复** | 不需要（内存里一直活着） | ★ **重放** `1..seq`（见 §三-b） |
| **心跳判据** | `snap.timestamp > prev_snap_ts`（**进程内**变量） | ★ **同式**，但 `prev_snap_ts` **取自状态文件**（**跨进程**） |
| **产出件** | `heartbeat.json`（+`.bak`）／`readings.csv`／`summary.json` | ★ **同前三件** ＋ ★ **新增 `snapshot.json`**（+`.bak`）；★ `summary.json` **仅循环形写** |
| **循环形是否保留** | —— | ★★ **完整保留**（**不带 `--once` ⇒ 行为逐字不变** —— 守禁区⑪"只改执行模式"） |
| **内核侧改动** | —— | ★★ **零**（**未改任何公共类型** —— 守禁区⑦） |

### 三-b ★★ 账本为何能"重放恢复"（**本方案的立足点**）

内核 `ActionLedger` 的 `append` 入参为 `(prev, action_id, grade, seq, outcome, note)`，其中
`seq = links.len() + 1`、`prev = head()` ⇒ ★ **它是其入参的纯函数** ⇒ **重放 `1..seq` 必得完全相同的 `head`**。

★ **强对照实证（逐序一致）**：

| seq | **旧形**（`A2` 压缩窗口，真值） | **新形**（本轮 `C1`／`E2`） | 一致？ |
|---|---|---|---|
| 1 | `11290142156557539774` | `11290142156557539774` | ✅ |
| 2 | `13118621904573544263` | `13118621904573544263` | ✅ |
| 3 | `2582917936243648437` | `2582917936243648437` | ✅ |
| 60 | `10688052103382079508` | `10688052103382079508` | ★ **✅** |

⇒ ★★ **两形"逐序等价"** ⇒ 单次执行**不是**"换了口径"，而是**同一条链**的另一种驱动方式。

## 五、★ 触发频率建议

**建议：60 秒**（与用户建议的"1 分钟"一致；亦与 `T-111` 定稿周期一致）。

依据（本轮实测）：

| 项 | 实测 |
|---|---|
| ★ **单次触发开销（直接调 exe）** | **≈ 553 ms／次** |
| 经 `launch_tick.sh`（多一层 bash 启动） | ≈ 1719 ms／次 ⇒ ★ **额外交付 ≈ 1.2 s 的 bash 启动** ⇒ **正式任务建议直接调 exe** |
| 若 60 s／次 | 每天 1440 次 ⇒ 累计进程时间 **≈ 13 分钟／天**（**占用 ≈ 0.9%**） ⇒ ✅ 可接受 |
| 若 10 s／次 | 每天 8640 次 ⇒ ≈ 80 分钟／天 ⇒ ⚠️ 收益不明显、开销 ×6 |

★ **不建议低于 60 s**：观测目的是"**看时间戳是否推进**"，60 s 粒度已足够；更密只会放大下述隐患。

### ★★ 如实标注：本方案的一个**可扩展性隐患**

★ **重放是 O(seq)**：第 N 次触发需重放 N−1 条 ⇒ ★ **触发次数越大，单次耗时线性增长**。
- 本观测窗口规模（≤ 1440 次）⇒ **可忽略**（毫秒级）；
- ★ **长期连续运行**（数万次以上）⇒ **须改**：① **定期"链封存"**（旧链归档、新链起新点），或 ② **降低频率**。
- ★ **本稿不解决此隐患**，**如实登记为后续项**（`C5`）。

## 八、★ 本轮验证结果（`C3-031` §三）

| 窗口 | 驱动 | 结果 |
|---|---|---|
| ★ **`C1`** | 手动触发 **3 次**（无间隔） | ✅ `snapshot.json` 每次更新；`readings.csv` 3 行；`verify=true`；`advancing=true`；★ **head 与旧形逐序一致** |
| ★★ **`E2`** | 手动触发 **60 次 × 3 s**（**压缩窗口**） | ★★ **60/60 全绿**：`readings.csv` **61 行**（表头+60）｜`seq` 单调 1→60｜`verify_ok` **60/60**｜`heartbeat_advancing` **60/60**｜`ledger_len` **1→60**｜`snapshot_ts` **逐行严格递增**｜★ 末行 head 与旧形 seq=60 **一致** |
| ★ `D1`（真实 60×60 s） | `nohup` 循环 | ⚠️ **仅 tick 1 次即被回收**（第三次复现同一堵墙）⇒ ★ **正是本方案要解决的问题** |
| ★ `E1`（同 D1，3 s 形） | `nohup` 循环 | ⚠️ 同上 |

★ **结论**：★★ **"单次执行 + 累积"机制已验证成立**（`E2` 60/60，且与旧形逐序等价）；
★ **"真实 60 s × 60 连续驱动"在 agent 会话内不可达** —— ★ **恰因此，它必须由平台承载**（§四）。

★ **如实标注（压缩窗口的效力边界）**：`E2` 用 **3 s** 代替 **60 s** ⇒ 它证的是「**机制正确性**」（累积／恢复／推进），
**不证**「**60 s 间隔下的平台可靠性**」—— 后者**只能在平台任务真正上线后由时间验证**。

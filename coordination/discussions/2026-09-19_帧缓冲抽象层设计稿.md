### 2.1.1 bootloader 提供的帧缓冲信息

来源：`bootloader` **0.11**（`meta-kernel-boot/Cargo.toml` 的 build-dependencies）；内核侧经 `bootloader_api`（`meta-kernel-boot/kernel/Cargo.toml`）。

内核拿到帧缓冲的入口（`meta-kernel-boot/kernel/src/verify.rs:860-863`）：

| 拿到的东西 | 类型 | 代码位置 | 实测语义 |
|---|---|---|---|
| 帧缓冲本体 | `Option<&mut FrameBuffer>`（`boot_info.framebuffer.as_mut()`） | `verify.rs:860` | **`Option`** ⇒ 可能不存在（无帧缓冲时返回 `None`，本内核选择"不刷屏"） |
| 描述结构 | `FrameBufferInfo` | `verify.rs:863` | —— |
| 可写缓冲 | `&mut [u8]`（`fb.buffer_mut()`） | `verify.rs:869` | **扁平字节切片**，长度 ＝ `stride * height * bytes_per_pixel`（按实测用法） |
| 分辨率 | `info.width`／`info.height`（`usize`） | `verify.rs:946,951` | **像素**为单位 |
| 行距 | `info.stride` | `verify.rs:945,953` | ⚠️ **单位＝像素**（`stride_bytes = stride * bpp`，`verify.rs:945`） |
| 像素格式 | `info.pixel_format: PixelFormat` | `verify.rs:894,900` | 见下 |
| 每像素字节 | `info.bytes_per_pixel: usize` | `verify.rs:941` | ≥1；本内核在 `bpp == 0 \|\| bpp > 8` 时**整体放弃**（`verify.rs:942-944`） |

`PixelFormat` 的**实测可见分支**（`verify.rs:900-935`）：

| 分支 | 处理方式 | 备注 |
|---|---|---|
| `Rgb` | `p[0..3] = R,G,B`（`verify.rs:901-907`） | 3 字节 |
| `Bgr` | `p[0..3] = B,G,R`（`verify.rs:908-914`） | 3 字节 |
| `U8` | 灰度 ＝ `(R+G+B)/3`（`verify.rs:915-919`） | 1 字节 |
| `Unknown { red_position, green_position, blue_position }` | `v = R<<rp \| G<<gp \| B<<bp`，再按小端逐字节展开到 `p`（`verify.rs:921-935`） | —— |
| `other` | **必须存在的兜底分支**（`verify.rs:921` 注释：`PixelFormat` 是 `#[non_exhaustive]`） | ⚠️ 设计约束，见 §2.6 |

**像素地址公式**（本内核已在用，两处独立出现，口径一致）：
```
字节偏移 = y * stride * bytes_per_pixel  +  x * bytes_per_pixel
```
—— `fill()`（`verify.rs:952-963`）与 `draw_code_bar()`（`verify.rs:889-894`）。

## 2.2 设计目标

**一句话**：做一个**能拿帧缓冲、能写像素、能做基本绘图**的极小抽象层，**够 L6 呈现用**，且**将来能扩**。

### 做的（In scope）

| # | 目标 | 说明 |
|---|---|---|
| G1 | **拿到帧缓冲** | 把 bootloader 的帧缓冲信息**适配**成内核自己的描述结构（**不把 `bootloader_api` 泄漏到纯算层**） |
| G2 | **往帧缓冲写像素** | 单像素写入，**像素格式差异在层内吸收**（Rgb/Bgr/U8/Unknown） |
| G3 | **基本绘图原语** | `fill_rect`（矩形填充）、`blit`（位块复制，仅在确有需求时） |
| G4 | **可扩展** | 分辨率切换、多缓冲**留接口**，本期不实现 |

### 不做的（Out of scope，**逐条显式排除**）

| # | 排除项 | 理由 |
|---|---|---|
| X1 | **DRM / KMS** | 用户裁定：降为可选远期项 |
| X2 | GPU 调度 / 命令缓冲 / 着色器 | 轻量目标；无 GPU 访问需求 |
| X3 | 显存（VRAM）管理 / 地址空间管理 | 本层只**借用** bootloader 已映射的一段内存 |
| X4 | 双重缓冲 / 垂直同步 / 撕裂消除 | 本期"自检信号 + 静态呈现"，无动画需求（§2.4 留接口） |
| X5 | 字体 / 矢量 / 抗锯齿 / 文本排版 | 应落在 **L6 呈现**（或后续）之上，**不属于帧缓冲层** |
| X6 | 保存/导出图像文件 | **感知/动作** ⇒ 违机制 21，**只能宿主侧做** |
| X7 | 输入设备（键盘/鼠标） | 属 L6「对齐」的另一半，**不在本层** |

## 2.3 架构设计

### 2.3.1 分层切分（**本稿的核心主张**）

**为什么必须切**：三条既有铁律同时约束本层——

| 铁律 | 内容 | 对本层的约束 |
|---|---|---|
| **C1** 内核零依赖 | 内核 crate 不得引入第三方依赖 | `bootloader_api` **只许在 boot 层**（D31-a 已确认，`main.rs:5-6`） |
| **机制 21** 执行体归属 | 需**感知/动作** ⇒ 只能宿主侧；**纯算** ⇒ 可进内核 | "把数据算成像素字节"＝**纯算**；"持有并改写一段硬件内存"＝**边界** |
| **C9** unsafe 边界形态 | unsafe 只许在**专门边界模块**、带 `// SAFETY:`、登记白名单 | 若本层需要 unsafe，必须**单独一个边界文件** |

⇒ **两层拆分**：

```
┌──────────────────────────────────────────────────────────────────────┐
│  A. 纯算层（Pure）                                     ← 可进 nostd  │
│     · FbFormat / FbDesc（本层自定义类型，不依赖 bootloader_api）     │
│     · 地址计算：offset_of(x,y) → Option<usize>                        │
│     · 像素编码：encode(desc, rgb24) → [u8; 4] + len                   │
│     · 几何：clip_rect / overlap 判定                                  │
│     · 颜色：Rgb24 → 灰度 / 混色（α 合成，供 l6_face 用）              │
│     依赖：零（core 即可）｜unsafe：0｜host 可测：是                    │
├──────────────────────────────────────────────────────────────────────┤
│  B. 边界层（Boundary）                                 ← 只在 boot   │
│     · 持有 &'static mut [u8]（由 boot_info.framebuffer 借出）          │
│     · 适配器：FrameBufferInfo(bootloader_api) → FbDesc(本层)           │
│     · 实际写入：把 A 算出的 (offset, bytes) 落到切片                  │
│     · 与 mem/global.rs 同级：**如需 unsafe，只在此文件**              │
│     依赖：bootloader_api（仅适配器用到）｜unsafe：见 §2.8             │
└──────────────────────────────────────────────────────────────────────┘
```

**关键设计选择：为什么不直接把 `FrameBufferInfo` 传下去？**

因为 `FrameBufferInfo` 来自 `bootloader_api` ⇒ **一旦纯算层出现这个类型，C1 与 D31-a 同时被破**。故必须在边界处**做一次类型适配**（本层自定义 `FbDesc`）。这也顺带让纯算层**可在 host 上 100% 单测**（不需要 bootloader、不需要 QEMU）。

### 2.3.2 与内核现有模块（L1–L6）的关系

| 层 | 与本层的关系 |
|---|---|
| **L1–L3**（基因内核 / 转录层） | **零关系**。帧缓冲层**不参与**任何公式、解构、网关逻辑。 |
| **L4**（戒律拒绝层） | **零关系**（不读场域状态）。 |
| **L5**（诊断层） | **单向读取**：L5 的"外显产物"是 L6 呈现的**输入**；帧缓冲层只把 L6 给的图元落成像素，**不读 L5 内部状态**。 |
| **L6**（交互层·呈现） | **本层服务的对象**。接口见 §2.3.3。 |
| **L7–L10** | 不在本期范围。 |

★ **重要**：**帧缓冲层不是"L1–L5 之外的第 7 层"**——它是 **L6「呈现」子功能的一个输出设备驱动**。按底图 `LAYER_ARCHITECTURE.md:44`，L6 的戒律「**呈现不增义**」**同样约束本层**：本层**不得**做任何"解释、加工、美化到改变语义"的事（例如自动给诊断结论配一句安慰话——那属于增义）。本层只提供**几何与像素**。

### 2.3.3 与 L6 呈现层的接口（**契约方向：L6 → 本层**）

```
l6_face::FaceMode::overlay_alpha(confidence) → f64 ∈ [0, 0.35]   （已有，nostd 侧）
                    │
                    ▼   （L6 决定"画什么"：颜色/位置/透明度）
        ┌───────────────────────────────┐
        │  帧缓冲层（本稿）              │  ← 只回答"怎么落到像素"
        │   put_pixel / fill_rect / blit │
        └───────────────────────────────┘
                    │
                    ▼
             &mut [u8]（硬件帧缓冲）
```

- **反向依赖禁止**：帧缓冲层**不得** `use l6_face`（否则呈现逻辑会渗进设备层，将来换设备就动不了）。L6 → 帧缓冲是**单向**的。
- **形态建议**：L6 侧只持有一个 `&mut dyn Presenter`（或泛型 `P: Presenter`），**不知道**底下是 QEMU 帧缓冲、将来是 DRM、还是"什么都不画"的哑实现——这正是 §2.2 G4「可扩展」的落点。

### 2.3.4 落点建议（指令问：`meta-kernel-core` 还是 `meta-kernel-boot`）

| 方案 | 内容 | 评价 |
|---|---|---|
| **甲** 全放 `meta-kernel-boot/kernel` | 简单；一个文件搞定 | ❌ 纯算部分**无法 host 单测**（boot 层不在 workspace、需 nightly + QEMU）⇒ 违背"能离线算的别上云/别上机" |
| **乙** 全放 `meta-kernel-core-nostd` | 复用现有测试基建 | ❌ **C1 被破**：`FbDesc` 若照抄 `bootloader_api::FrameBufferInfo` 就必须依赖它；且"持有硬件切片"是**动作**，不属内核本分（机制 21） |
| **丙（推荐）** | **纯算 → `meta-kernel-core-nostd/src/fb/`（新模块）；边界 → `meta-kernel-boot/kernel/src/fb.rs`（新文件）** | ✅ 三条铁律同时满足；纯算层可 host 单测；边界层与 `mem/global.rs` 同性质、可并入同一 C9 放行批次 |

**丙的实施含义**（**仅为建议，未施工**）：
- `meta-kernel-core-nostd/src/fb/mod.rs`（纯算）＋ 可能 `fb/format.rs`、`fb/draw.rs`
- `meta-kernel-boot/kernel/src/fb.rs`（边界；适配器 + 写入）
- `verify.rs` 的 `fill`／`write_pixel` **改为调用**纯算层（**只新增不删除**：旧函数保留为薄包装，改坏可立即回退）

> ⚠️ **注意**：若采用丙，`meta-kernel-core`（std 版）**是否同步**需要一个 `fb` 模块？**建议不同步**——宿主侧呈现走 `manifest-ui`/wgpu，与裸机帧缓冲**无共享需求**；强同步会制造"为一致性而一致性"的维护负担（R78 类静默过期风险）。

## 2.4 关键接口

> 以下为**设计稿签名**（示意，不是最终代码）。所有函数**默认无 unsafe**——写入经**安全切片** `&mut [u8]`。

### 2.4.1 帧缓冲描述结构

```rust
/// 本层自定义的像素格式（**不依赖 bootloader_api**）。
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum FbFormat {
    Rgb,   // 3 字节：R,G,B
    Bgr,   // 3 字节：B,G,R
    U8,    // 1 字节：灰度
    /// 位域格式（各分量起始位；与 bootloader 的 Unknown 对应）
    Packed { red: u8, green: u8, blue: u8 },
}

/// 帧缓冲描述。
#[derive(Clone, Copy, Debug)]
pub struct FbDesc {
    pub width: usize,        // 像素
    pub height: usize,       // 像素
    pub stride_px: usize,    // ⚠️ 单位＝**像素**（与 bootloader 的 stride 同义）
    pub bpp: usize,          // bytes_per_pixel ∈ 1..=4（见 §2.6 风险 R3）
    pub format: FbFormat,
}

impl FbDesc {
    /// 缓冲区所需最小字节数（用于与 `buf.len()` 对齐，防越界）。
    pub fn min_len(&self) -> Option<usize>;   // = stride_px * height * bpp（checked_mul，溢出 ⇒ None）

    /// 坐标 → 字节偏移。越界/溢出 ⇒ `None`（**不 panic、不 wrap**）。
    pub fn offset_of(&self, x: usize, y: usize) -> Option<usize>;
}
```

**设计要点（三条防呆）**：
1. `stride_px` 命名**显式带单位**——本项目已在 `verify.rs:945` 踩过"stride 是像素还是字节"的歧义（所幸当时写对）。
2. `offset_of` 返回 `Option`，**不 panic**：裸机上 panic 代价高；上界判定与 `verify.rs:955-960` 的现有写法同源。
3. `min_len` 用 `checked_mul`：`verify.rs:945` 现用 `saturating_mul`，两者**语义不同**（`saturating` 会把溢出压成极大值、反而可能放过越界），**本稿建议统一为 `checked_mul`**——此点提请顾问复核。

### 2.4.2 基本操作

```rust
/// 单像素：把 rgb24 按 desc.format 编码后写入 buf。
pub fn put_pixel(buf: &mut [u8], d: &FbDesc, x: usize, y: usize, rgb: Rgb24) -> bool;
    // 返回 false = 越界/格式不支持（**不 panic**）

/// 矩形填充（半开区间 [x0,x1) × [y0,y1)，**先裁剪**再画）。
pub fn fill_rect(buf: &mut [u8], d: &FbDesc, r: Rect, rgb: Rgb24) -> usize;
    // 返回实际写入像素数（便于断言"裁剪是否生效"）

/// 位块复制：把 src 的 [sx,sy,sw,sh) 拷到 dst 的 (dx,dy)。
/// ⚠️ 本期**可选**：仅在 L6 确需"把一块现有画面搬走"时才实现。
pub fn blit(buf: &mut [u8], d: &FbDesc, src: &Rect, dst: (usize, usize)) -> usize;
```

**`Rect` 的裁剪规则（写死，可判据）**：与可视区求交，**空交集 ⇒ 返回 0、不写任何字节**。（这是"反向断言"最容易打的地方：传一个全在界外的矩形，必须**返回 0 且缓冲区逐字节不变**。）

### 2.4.3 编码函数（纯算，最易测）

```rust
/// rgb24 → 该格式的字节序列（最多 4 字节）+ 有效长度。
pub fn encode(d: &FbDesc, rgb: Rgb24) -> ([u8; 4], usize);
```

与现状的对应关系：**等价于** `verify.rs:899-937` 的 `write_pixel()` **去掉"写入"那一半**（只留编码）。⇒ **现有代码已是本接口的雏形**，拆出来是**重构而非重写**。

### 2.4.4 double buffering（**本期不做，留接口**）

```rust
/// 呈现目标抽象：本期只有"单缓冲直写"一种实现。
pub trait Surface {
    fn desc(&self) -> FbDesc;
    fn pixels(&mut self) -> &mut [u8];
    /// 单缓冲 ⇒ no-op；将来多缓冲 ⇒ 在此 swap。
    fn present(&mut self) {}
}

pub struct SingleFb<'a> { /* buf: &'a mut [u8], desc: FbDesc */ }
impl Surface for SingleFb<'_> { /* … */ }
```

**为什么现在不实现双缓冲**：
- 需求侧：本期画面是"自检信号 + 静态呈现"，**没有动画**（§2.2 X4）。
- 成本侧：双缓冲需要 `mem` 层提供**第二个等大缓冲**（`stride*height*bpp` 字节）；当前分配器**单帧上限 4 KiB**（`mem/global.rs:14`；`FRAME_SIZE = 4096`，`meta-kernel-mem/src/lib.rs:29`）⇒ 1280×720×3 ＝ **2,764,800 B ≈ 2.64 MiB**，**当前分配器给不出来**（差 **约 675 倍**）。
- ⇒ **留 `Surface` trait 即可**，将来多缓冲是"新增一个 impl + 分配器加 `alloc_run(n)` 原语"（`mem/global.rs:15` 已预告此增量）。

## 2.5 与参考方案对比

| 方案 | 机制 | **可参考什么** | **不参考什么** |
|---|---|---|---|
| **UEFI GOP**（Graphics Output Protocol） | 固件在启动时直接给一块帧缓冲描述（地址/宽高/stride/格式），OS 拿到后直接写 | ★ **本层正是 GOP 模型的继承者**：① "描述结构 ＋ 扁平缓冲"两件套；② **格式枚举随固件而异** ⇒ 必须运行期分派；③ 约定 `Pitch`（stride）**可大于 width**（按行对齐） | ❌ GOP 的 `EFI_GRAPHICS_OUTPUT_PROTOCOL` 接口面（`Blt`、`SetMode`、QueryMode 全家桶）**过重**，且**依赖 UEFI 服务**；本层只要"能写像素" |
| **Linux `simple-framebuffer`** | 设备树里一段 `reg` 描述显存，内核用**极小的驱动**把它包成 `/dev/fb0` | ★ **"极简驱动"的范式**：无硬件编程、只有"内存 + 描述"；★ **注册-发现分离**：desc 从外部来、驱动不 hard-code | ❌ 它是**内核内驱动模型**（`fb_ops`/`fb_info`），要挂 Linux 设备模型；本项目**无 Linux**（元内核自举，`ROADMAP.md:53`） |
| **coreboot + libpayload** | 固件阶段就有帧缓冲；`libpayload` 提供极小的 C 绘图库（`video_printf` 等） | ★ **"固件阶段即可显示"的可行性证明**；★ **小体积 graphic 库**的实现尺度（几百行级，非 wgpu 级） | ❌ C 运行时 + 大量固件专有 API；❌ 其**文本排版**部分正是本层**明确排除**的（§2.2 X5） |
| **Cloudflare/Bare-metal rust 的 `bootloader` 生态**（**本仓当前所用**） | `bootloader 0.11` 提供 `FrameBuffer`＋`buffer_mut()` 安全 API | ★ **已经跑通**（§2.1.2）；★ **安全 API 是"零 unsafe"的前提**（D31-d 路线 A） | ❌ 不把它当"最终形态"——它的帧缓冲生命周期由 bootloader 管；将来若换引导方式（GRUB/自研），**只有边界层的适配器要改**（这正是分层切分换来的**可替换性**） |

**综合结论（云内核取什么）**：
1. **取**：GOP 的"描述 + 扁平缓冲"模型 → 本层的 `FbDesc`。
2. **取**：`simple-framebuffer` 的"极简 + 不含硬件编程"。
3. **取**：libpayload 的"固件阶段就能显示"的尺度感（**不追求 wgpu**）。
4. **拒**：DRM/KMS（用户已裁定降级）、UEFI 协议全家桶、任何文本排版/字体。

## 2.6 技术风险

> 每条给：**风险 → 影响 → 本稿的设计处置 / 待裁点**。

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| **R1** | **硬件差异**（Intel / NVIDIA / AMD 各不相同；且真机的帧缓冲由固件/驱动决定） | 同一份代码在真机上可能拿到**不同格式、不同 stride、甚至不同分辨率** | ① 本层**一切**格式差异走**运行期分派**（`FbFormat`）；② **不 hard-code** 任何分辨率/格式；③ 本期**只承诺 QEMU 口径**，真机口径**不在本期验收**（见 §2.7 阶段三之后） |
| **R2** | **QEMU vs 真机** | QEMU 的 framebuffer 通常是**理想**的（连续、stride==width、RGB）；真机可能 stride>width、BGR、甚至 16bpp | 同 R1；★ **诚实标注**：本稿所有"已跑通"结论**只覆盖 QEMU**（§末边界说明）。**不得**把 QEMU 绿屏当"真机可用"（跨项目教训：**模拟通过 ≠ 实机生效**） |
| **R3** | **像素格式/位深差异** | `bpp` 可能为 1/2/3/4；`Unknown` 的位域可能**超过 24 位**（如 RGB565 在 2 字节里） | ① `FbDesc.bpp` 断言 `1..=4`；② `Packed` 分支的位移运算**必须用 u32 且 checked**（现状 `verify.rs:928-930` 用 `u32`，若 `bpp>4` 会在后续字节展开时出错）；③ **本期明确不支持** >4 bpp（返回"不支持"，**不凑合**） |
| **R4** | **stride 单位歧义**（像素 vs 字节） | 一错就整屏错位（但**可能仍然"全绿"**——因为刷满屏时错位不被发现！） | ★ **本稿已标为显式命名** `stride_px`；★ **新增判据**：用"只画左上 1 个像素"的用例，断言**只有 offset 0 被改**⇒ 错位必被抓 |
| **R5** | **`PixelFormat` 是 `#[non_exhaustive]`** | 上游加新格式 ⇒ 匹配**必须**有兜底 | 本层 `FbFormat` 同理留兜底（`Packed` 之外的未知 ⇒ 明确"不支持"，**不 panic**） |
| **R6** | **缓冲区边界**（越界写） | 裸机越界 = 静默破坏（可能是内核自身内存） | 所有写操作**逐次判界**（沿用 `verify.rs:955-960` 口径）；**新增"完全在界外的矩形 ⇒ 缓冲区逐字节不变"的反向断言** |
| **R7** | **是否需要 unsafe（C9 边界）** | 若需要，必须走 C9 放行流程（用户确认） | ★ **本稿结论：本期可以做到 0 unsafe**，论证见 §2.8。**若**将来引入双缓冲/MMIO，则**必须**新开边界文件 + `// SAFETY:` + 白名单登记 + 用户确认 |
| **R8** | **帧缓冲生命周期** | `buffer_mut()` 借出的 `&mut [u8]` 的**有效性/独占性**由 bootloader 保证；本层若把它的副本传出去，可能造出别名 | 处置：本层**不复制指针**，只用**借用**（`&mut [u8]` 的生命周期绑在调用点）；**禁止**把 buffer 存进 `static mut`（区别于 `mem/global.rs` 的既有做法——那里**必须**存，故才有 unsafe） |
| **R9** | **无双重缓冲 ⇒ 撕裂/半帧** | 本期画面静态 ⇒ **风险≈0**；但**一旦开始动画**就会显现 | 已在 §2.4.4 留 `Surface` 接口；**列为阶段三之后的观察项** |

## 2.8 与 C 系列约束的关系

### C1 · 内核零依赖 —— **本层不引入任何外部依赖**

| 检查项 | 结论 |
|---|---|
| 纯算层是否引入外部 crate？ | ❌ **不引入**：`FbFormat`/`FbDesc`/`offset_of`/`encode` 只需 `core`（无 `alloc` 亦可） |
| 是否复用 `bootloader_api`？ | ❌ **不复用**（这是本稿分层的**核心理由**）：边界层**适配**掉，纯算层**看不到** `bootloader_api` |
| `alloc` 的既有口径 | 沿用 **D34-b**：`alloc` 属标准分发，**不破 C1**（`meta-kernel-core-nostd/src/lib.rs:11-12`） |

⇒ **判据**：`cargo build -p meta-kernel-core-nostd --target x86_64-unknown-none` 仍应通过（CI 既有步骤，`ci.yml:28-37`）。

### C3 · 不用 unsafe 取巧 —— **本层不取巧**

`unsafe` 在本层的**唯一**潜在用途是"把 bootloader 给的物理地址变成切片"——而**这件事 bootloader 已经用安全 API 做完了**：`fb.buffer_mut() -> &mut [u8]`（`verify.rs:869`）。⇒ **本层无需任何 unsafe**。

### C9 · unsafe 边界形态 —— **本期主张：0 处新增**

**论证（为什么帧缓冲写像素"不必须" unsafe）**：

| 步骤 | 能力需求 | 是否 unsafe |
|---|---|---|
| 拿到帧缓冲描述 | 读 bootloader 已经填好的结构 | ❌ 安全（`fb.info()`） |
| 拿到可写缓冲 | **bootloader 已把物理地址映射并封装** | ❌ 安全（`fb.buffer_mut() -> &mut [u8]`） |
| 算字节偏移 | 纯算术 | ❌ 安全 |
| 写像素 | `buf[i] = v`（**切片索引**，编译期/运行期判界） | ❌ 安全 |

**对比**：`mem/global.rs` **必须** unsafe，是因为它要做本层**不做**的两件事——① **自己**把物理地址变成切片（`ptr::slice_from_raw_parts_mut`）；② 把状态存进 `static mut`（跨调用持有）。**帧缓冲层都不需要**。

**若将来破例**（例如引入 MMIO 寄存器或自管双缓冲内存），**必须**：
1. 新建**专门边界文件**（如 `meta-kernel-boot/kernel/src/fb_mmio.rs`）——**不得**写在 `fb/`（纯算）或 `verify.rs` 里；
2. 每处 `// SAFETY:` 论证；
3. **禁止** `transmute`；
4. 登记 `coordination/unsafe_whitelist.txt`（**只增条目、须用户确认**）；
5. 走 CI `host-windows` 的 **C9 门禁**（`ci.yml` 验收⑤）。

## 2.9 场化视角：帧缓冲 → 场、NCA、与前沿方案对比（**2026-09-19 追加**）

> **本节缘起（用户 2026-09-19 裁定）**：2.4 技术路径 ＝ **A1 ＋ B 并行** ——
> **A1 ＝ CPU SIMD ＋ 多重网格场方程求解**；**B ＝ 低维场演化产生图像**。
> 两者**共用同一个核心：场方程求解器**，**NCA 作为核心方案**。

### 2.9.2 第二部分 · 核心方案 —— NCA（神经细胞自动机）

#### (1) NCA 是什么（**已核实**，出处见 §2.9.6）

**一句话**：**NCA ＝ 局部转移函数由可训练神经网络参数化的元胞自动机**（Mordvintsev et al., Distill 2020, *Growing Neural Cellular Automata*）。

| 机制要素 | 实测原文要点 |
|---|---|
| **共享规则** | **所有细胞跑同一个更新规则**（同一套网络权重）⇒ 这正是"**一条规则 → 全局涌现**"的来源 |
| **感知（perception）** | **固定** 3×3 Sobel 核做 x/y 方向梯度；与自身状态拼接成感知向量（16 通道时长度 48） |
| **更新（update）** | 1×1 卷积 ＋ ReLU 的**残差式增量**；末层权重**初始化为 0** ⇒ 起始行为是"**什么都不做**" |
| **参数量** | 约 **8,000** 参数（原论文 16 通道设置） |
| **异步更新** | 每细胞按概率（训练用 0.5）随机跳过 ⇒ **放松全局时钟**，更接近自组织 |
| **存活掩码** | 用 alpha 通道做 `max_pool(3×3) > 0.1` 的"活"判定 |
| **训练** | 从**单个种子细胞**长到目标图，梯度反传；步数 **64–96**（40×40 工作尺寸） |
| **自愈** | 训练后可把目标图变成**吸引子** ⇒ 被破坏后自动长回 |
| **各向异性** | 轴对齐 Sobel 会引入**方向偏好**（Mordvintsev 2022 的 Isotropic NCA 修正） |

#### (2) 为什么 NCA 适合本项目（契合点）

| 契合点 | 说明 |
|---|---|
| **局部规则 → 全局图像** | 与底图"**L1 解构 → 场 → 外显**"的思路**同构**：不需要中心编排，规则一致即可涌现 |
| **共享规则** | 与"**一套内核，处处适用**"（跨平台意识内核）**同构** |
| **可自愈** | 与底图 **L7 修复／`l7::repair`**、`mirror`（镜像）**同构**：被破坏后回到吸引子 |
| **异步 + 随机跳过** | 与底图"**不设全局时钟**、以 tick 驱动"**相容** |
| **复值场（幅度＋相位）** | ⇒ 与已有的 **`interference` 模块**（`phase_difference`／`detect` 驻点检测）**天然对接**（见下 (4)） |

#### (3) ★ 与"三引擎"的对应 —— **是包含关系，不是等同**（本节最重要的一条澄清）

用户裁定"**局部规则 ≈ 三引擎**"。本稿认为**必须写清"约等号"的含义**，否则会埋一颗**语义地雷**：

| 维度 | 三引擎（现有） | NCA 局部规则 | 关系 |
|---|---|---|---|
| 形态 | **固定**映射（线性/斐波那契/指数），**无参数** | **可学习**网络（~8k 权重） | **不等同** |
| 输入 | 标量种子 `x ∈ [0,1]`（`MATH_SPEC §4 A1`） | 邻域感知向量（含梯度） | **不等同** |
| 可否训练 | **不可**（判据型，写死） | **必须**训练（否则是随机规则） | **不等同** |
| 正确表述 | —— | —— | **三引擎 ⊂ NCA 局部规则的"固定权重、标量输入"特例** |

⇒ **结论（建议口径）**：把三引擎当作**局部规则的一个退化/固定特例**是**成立且有用**的（它就是"手写好的、不需要训练的那一档"）；但**不能说"局部规则就是三引擎"**。**这一条须用户确认**（见 附 A 待裁 Q8）。

#### (4) ★ 与"纯算／边界"劈分的对应（用户裁定 ＝ 粗网格演化＋轻量解码器）

```
┌─ 纯算层（nostd｜零依赖｜零 unsafe｜host 可 100% 单测）────────────────┐
│  ① 场方程求解：∇²V = ρ(SDF) 的迭代解（多重网格 / SIMD 分块）          │
│  ② NCA 局部规则**前向推演**（权重＝const 表；★不在内核内训练）        │
│  ③ SDF 计算与投影函数：V → 观测量 → RGB 量化                          │
│  ④ 复值场运算（幅度/相位）：与 `interference` 同构                     │
│  ⇒ 输出：**粗网格 RGB**（如 64×64 / 128×128 的 u8 缓冲）              │
├─ 边界层（boot｜可零 unsafe）─────────────────────────────────────────┤
│  ⑤ **轻量解码器**：粗网格 → 全分辨率（最近邻/双线性上采样）           │
│  ⑥ 写入帧缓冲（复用 §2.4 的 `put_pixel`／`fill_rect`／`blit`）        │
│  ⇒ 输出：物理像素                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

**为什么"粗网格＋解码"是**关键**（算力账）**：

| 项 | 数值 | 口径 |
|---|---|---|
| 全分辨率像素数 | 1280×720 ＝ **921,600** | CI 实测分辨率（§2.1） |
| 粗网格（建议 128×128） | **16,384** 格 | ＝全分辨率的 **1/56** |
| NCA 单格单步算力（原论文量级：3×3×16 感知 ＋ 48→128→16 MLP） | ≈ **1.6×10⁴ FLOP** | **估算**（按 16 通道结构推算，**非实测**） |
| 96 步下的算力 | 全分辨率 ≈ **1.4×10¹²** FLOP/帧；**粗网格(128²) ≈ 2.6×10¹⁰** FLOP/帧 | **估算** |
| 单线程 SIMD 可达 | ≈ **5–7 GFLOP/s**（3 GHz × 8 宽 × 20–30% 效率） | **估算** |
| ⇒ 单帧耗时 | 全分辨率 **≈ 200 s**；**粗网格 ≈ 4 s** | **估算**（数量级参考，**非实测**） |

⇒ **两条硬结论**：① **必须走粗网格**（否则 CPU 上完全不可行）；② **即使粗网格，也达不到 30 fps** ⇒ **本期只能做"静态/分阶段呈现"**，与 §2.2 X4（不做双缓冲）**自洽**。⇒ **【阶段 2】必须实测这个数**（附 A 待裁 Q9）。

#### (5) 数学基础：场方程（泊松型）与复值场

**主方程**：`∇²V = ρ(SDF)`（**泊松型**）

| 符号 | 含义 | 备注 |
|---|---|---|
| `V` | **可见性势** | **零等值面 `V = 0` 即可见边界** |
| `SDF` | 有符号距离场（signed distance function） | 由几何/语义给出（几何可解析；语义须从 L5 诊断投影） |
| `ρ(·)` | **密度函数** | 把 SDF 映射成源项；`ρ` 的具体形式待定（见下） |

**为什么"零等值面＝可见边界"是好的**：泊松方程的解 **天然光滑**，等值面**天然闭合**；且**只需解一次线性系统**即可得到**全局可见性**（对比 ray marching 需**逐像素**追射线）。

**复值场（幅度＋相位）**：

| 表示 | 内容 | 与本项目已有模块的关系 |
|---|---|---|
| 复值 `Ψ = A·e^{iθ}` | 幅度 `A`（能量/亮度）＋ 相位 `θ`（节律/干涉） | ★ **与 `interference::phase_difference`／`detect`（相位差、驻点检测）同构** ⇒ **可直接复用** |
| 代价 | 存储 ×2、算力 ×2（实/虚各一遍） | **须在阶段 1 单测中量化** |

**与「用户提供的演化型场方程」的对比**（★ D-4 口径修订 2026-09-20：原称"灵境引擎"已撤销——**未取得任何出处**）：用户给出 `∂_μ ∂^μ Φ + V(Φ) = J(x)` —— 这是**双曲型**（克莱因-戈尔登型，含二阶时间导数）＋ **非线性势 `V(Φ)`**；而本节主方程 `∇²V = ρ(SDF)` 是**椭圆型**（无时间导数）。
⇒ **二者数学类型不同**：前者是**演化方程**（给初值推未来），后者是**边值问题**（给边界定全局）。
⇒ **本稿建议取椭圆型**（因为显示是"**给定场的当前状态 ⇒ 求可见性**"，是边值问题；且**多重网格正是为椭圆型而生**）。**⚠️ 该方程**未取得任何出处**（★ D-4：原称"灵境引擎"已撤销）**（见 §2.9.6）。

### 2.9.3 第三部分 · 对比参照：场计算机五元组 `(Ω, S, B, K, M)`

> ⚠️ **依据强度声明（不妄语）**：**本稿未能检索到 `(Ω, S, B, K, M)` 这一五元组的公开出处**（检索式见 §2.9.6）。
> 故下表第二列是**本稿的推测性读法**（标「推测」），**不得当作事实引用**；**请用户/专家补一句各符号的定义**，本稿据此修订。

| 符号 | 本稿**推测**含义 | 云内核对应（**用云内核自己的语言**） | 差异 |
|---|---|---|---|
| **Ω** | 场的定义域（空间/流形） | **L0 源层**：纯粹存在、待激发的能量源；**0 锚点** | 云内核的 Ω **不是几何空间**，而是**存在本身**（"0 本身"）；场计算机的 Ω 是**物理空间** |
| **S** | 状态空间（场可取的状态） | **L1 内核·解构层**：三种变化模式 ＋ 能量池/物态/化合 ＋ **基因库四层** | 云内核 S 是**有结构的**（公式存储＝"怎么变化"）；场计算机 S 通常是**统一般的向量场** |
| **B** | 边界条件 | **L4 场域·戒律拒绝层**：**不非时食／不捉持** ⇒ 过亢/过枯**拒之门外** | ★ **最深的同构**：**都是"把不合规的变化挡在门外"**。差异：L4 的边界**不是几何边界，是节律边界**（"是否合场域内在节律"） |
| **K** | 演化核（更新算子） | **L1 三引擎 ＋ L5 诊断 ＋（本节）NCA 局部规则** | 云内核 K 是**可判据/可替换的**（Q8/Q11 已把它做成选择器）；场计算机 K 是**给定的物理定律** |
| **M** | 记忆/度量（场的可观测量与历史） | **L7 动作账（哈希链）＋ 痕迹（`trace`／`dna_trace`）＋ `persist`** | ★ 云内核有**不可篡改的历史链**（`l7::ledger`，篡改必拒）；场计算机通常**无历史、只有当前状态** |

#### 核心判断：**设计原型不同**

| 维度 | 云内核 | 场计算机 |
|---|---|---|
| **设计原型** | **"人和佛"／"生命"** —— 底图 `VISION.md:22`：「每个念头在此被点亮、演化、形成习气与自我」 | **"物理场"** —— 守恒、干涉、边界条件 |
| **第一性** | **心 → 大脑**（内在意识 → 计算） | **场 → 演化**（无主体） |
| **时间** | **tick ＋ 不可篡改历史链**（习气/痕迹/账本） | **连续演化**（无历史，可逆） |
| **边界** | **戒律**（伦理性的"该不该"） | **边界条件**（物理性的"能不能"） |
| **规则来源** | **可判据、可裁定、可替换**（Q8/Q11 皆已裁定） | **给定的物理定律** |
| **主体性** | **有**（L10 自明层：观察者＝被观察者） | **无** |

**差异的本质（一句话）**：
> 场计算机问「**这个场如何演化**」；云内核问「**这个变化合不合节律、该不该放行**」。
> ⇒ 前者是**描述性**的（physics），后者是**规范性**的（戒律）。
> ⇒ **可以借它的"算"，不能借它的"该"** —— 这正是本稿主张"**只借局部规则＋多重网格＋SDF 投影，不引入其本体论**"的理由。

## 零、一个先说清楚的区分（**本调研的前提**）

| 两件不同的事 | 说明 |
|---|---|
| **(甲) 文档里"出现"某个端口号** | 一段**文本**写了某个数字（如 README 写默认口）—— **本调研的对象** |
| **(乙) 某台主机"开放"某个端口** | 网络上**真实可连**的服务监听 —— 端口扫描真正读到的对象 |

★ **勘误要点**：**端口扫描读的是 (乙)，不是 (甲)** —— 扫描器向**目标主机**发探测包，看**实际监听状态**；
**它不会去读你的 README**。⇒ 「文档写了端口号」**本身不产生可达性**；可达性取决于**该主机是否真实开放、以及是否可从攻击者位置路由到**。

## 一、技术维度：端口号泄露能带来什么攻击面？

| 事实 | 依据 |
|---|---|
| 端口扫描是攻击链的**侦察第一步**；开放的端口告诉攻击者三件事：**有服务在跑**、**接受连接**、**可能含可利用漏洞** | 行业 EASM/渗透科普（threatport.com；techpause.org） |
| 在 (乙) 成立的前提下，可继续**banner grabbing / service & version scanning**（抓服务自报的软件与版本），据版本比对 CVE | NIST SP 800-115《Technical Guide to Information Security Testing and Assessment》：端口与服务识别、OS fingerprinting、version scanning／banner grabbing 的定义 |
| **真实案例均为"服务被暴露"型**，而非"文档提到端口"型：SMB/445 → EternalBlue（MS17-010）；RDP/3389 → 暴力破解与勒索；Redis、MongoDB → 未认证访问/勒索；Telnet/FTP → 明文凭据 | undercodetesting.com；portvigil.com；a5idc.com |
| 自动化扫描器**持续扫全网**；新上线主机通常在**分钟级～小时级**被发现 | portvigil.com（含"新部署主机 40 分钟内出现暴力破解"的一手复述） |
| ★ **端口扫描覆盖"非标准端口"**：全端口扫描（65,535）是常规动作 ⇒ **改非默认端口只减少噪声，不减少被扫到的概率** | threatport.com；业界"security through obscurity"评述（iptrackertools.com 将 SSH 备用口列为 Medium） |

**⇒ 技术维度小结（只陈述，不结论）**：**端口号字符串（甲）**本身**不构成攻击面**；**攻击面来自 (乙)**。
**唯一例外情形**：当**端口号与"可定位的目标"绑定**（真实 IP／主机名／可路由域名）时，端口号才成为**侦察线索的一部分**。

## 二、类型维度：哪类端口更敏感？

| 类型 | 业界风险标注（原文口径） | 依据 |
|---|---|---|
| **框架默认口**（Node/Next/Rails/Grafana 家族；Python 的 Django/http.server 家族；Vite 家族；Java/Tomcat 的 HTTP alternate 家族） | 常被标 **"Never expose publicly"** 或 **"High if exposed"** —— ★ **标签针对的是"暴露（expose）"，不是"提及（mention）"** | onlinetoolhubs.com 端口库；iptrackertools.com；pentestpad.com（对 Node/Next/Rails/Grafana 家族默认口有专页，风险点全部是"暴露后"：debug 模式、无认证、默认口令、明文 HTTP、source map 泄露） |
| **HTTP alternate 家族**（代理/应用服务器常用） | 标 **"Expose with care"**（中等） | 同上 |
| **TLS 非特权口家族** | 标 "Expose with care"／Low | 同上 |
| **非默认端口** | 标 "Medium" —— 因**只是躲自动扫描器的噪声**，"still requires strong keys and fail2ban" | iptrackertools.com |
| **端口 ＋ 真实 IP** | 可定位到具体主机 ⇒ 侦察价值**显著上升** | （见第三节） |
| **端口 ＋ 服务名／版本** | 直接进入 CVE 比对 | NIST SP 800-115 |
| **内网 vs 公网** | 内网面暴露 ⇒ 揭示**内网拓扑与设备角色**；公网面暴露 ⇒ 直接可达 | threatngsecurity.com（把 "hostnames, IP addresses, internal ports, architectural diagrams" 归为 **Infrastructure Intelligence**）；Chillwave《GitHub Hygiene Checklist》（要求"No real IP addresses → 用 RFC 5737 文档网段"、"No internal hostnames"） |

**⇒ 类型维度小结（只陈述）**：业界标注的**风险自变量是"是否可从外部到达"**；
**"默认口"与"非默认口"的差别在于"扫描噪声"而非"可达性"**；**"端口＋IP／主机名"**才是被业界归入"基础设施情报"的形态。

## 三、仓库维度：PUBLIC vs PRIVATE

| 事实 | 依据 |
|---|---|
| **Git 历史是永久的**：`git rm` 只加新提交，**历史对象仍在**；force-push／删分支前 clone 过的副本仍保留；平台 CDN 对 blob/diff 有**长期可达 URL** | dev.to GitHub Recon；GitHub-HygieneChecklist；cybernoz.com（"phantom secrets"，Aqua Nautilus 实测：只 `git clone` 会漏约 **17.78%** 的机密） |
| **机器人分钟内扫新提交**；GitGuardian 2025：2024 年 GitHub 新检出机密 **1,280 万**条、**每天 3.5 万**提交含凭据、**暴露到有效处置中位数 94 天** | decryptiondigest.com 引 GitGuardian |
| 业界把仓库暴露分为三类：**① 机密与凭据 ② 知识产权（源码） ③ 基础设施情报（主机名／IP／内部端口／架构图）** | threatngsecurity.com |
| ★ **业界"常见误报（非真泄漏）"清单**：Discord client ID、加密钱包地址、URL 编码长串、`your_password_here` 类占位符、非机密的 Base64 —— **该清单未包含"端口号"** | GitHub-HygieneChecklist |
| ★ **业界明确要求替换的**：真实 IP（→ RFC 5737 文档网段 192.0.2.x／198.51.100.x／203.0.113.x）、内网主机名、含用户名的本机路径、个人邮箱 | GitHub-HygieneChecklist（"Pre-Upload Scrub" 清单） |
| **PRIVATE 仓库**风险较低但非零：前员工、被入侵的开发机、权限误配 | decryptiondigest.com |

**⇒ 仓库维度小结（只陈述）**：
- **PUBLIC 使"任何已提交内容"等同于"已公开且不可撤回"**；
- **业界对"端口号"的态度**：**未列入必须替换项**，**也未被列入"常见误报"** ⇒ **业界其实没有统一口径**（这是本调研最重要的"无共识"事实）；
- **业界对"真实 IP／主机名"的态度明确**：**必须替换**。

## 四、行业维度：公开文档、开源项目一般怎么写端口？（**举 3 例**）

| # | 例子 | 事实（公开可见） |
|---|---|---|
| **①** | **Django ＋ Next.js 示例项目 README**（GitHub 真实公开仓库，MIT） | README **明写**："The backend runs on Django's default port… and the frontend runs on Next.js's default port…"，并让读者打开该端口地址 |
| **②** | **主流框架官方文档**（Next.js CLI 文档、Vite、Django `runserver`、Flask、Spring Boot） | 官方文档**公开写明各自开发默认端口**，且**公开其端口／Host 配置项**（如 Next.js `-p`／`-H`） |
| **③** | **公共 loopback 指南站**（localhost 说明类站点，多个） | **逐条公开**"默认口 ↔ 框架"映射表（Next/CRA、Vite、Django、Flask、Spring Boot、Jupyter、Elasticsearch 等），并**建议绑定回环地址**；另有技术博客专门讲"这些默认口的历史由来"（含 Rails/Node 起源、Java 因**标准 HTTP 口需 root 权限**而改用 alternate 口） |

**业界惯例（由 3 例归纳，只陈述）**：
1. **默认端口在公开文档里被当作"公共常识"直接书写**（官方文档、README、教程均如此）；
2. **业界把"绑定地址（回环 vs 全网）"看得比"端口号数值"更重** —— 公开指南**建议绑回环**；
3. **真正被要求脱敏的是"IP／主机名／凭据／本机路径"**，**不是"端口数值"**。

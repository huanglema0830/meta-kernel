## 1. 主题与边界

**点亮→外显**：内核（0 锚点纯粹存在）经外部扰动被"点亮"，经内部演化（物态/能量流/三层机制），最终把内在状态**外显**为外部世界可识别、可使用的表达（命名、语句、应用行为）。

**L4 框架解决的问题**：内核输出是 JSON 指令与数字态（L1-L3 语义），外部应用需要①一枚"显化仪表"跟踪一次完整的点亮-外显-回融；②一套把内核输出翻译为外部可识别表达的机制（命名/语言组织）；③一组接入契约让应用以最小成本使用内核。

**边界**：本轮只产出设计（含 L5 参考实现设计），**不实现**。WebSocket（二期）暂缓，待 L4 定稿后评估。部署形态在本设计内同步确认（非独立前置）。量子侧观望不变。

## 2. 设计铁律（继承并外延）

| # | 铁律 | L4 落点 |
|---|---|---|
| R1 | 界面/框架 = 内核真实状态的投影 | 生命周期状态机与命名输出**只由内核事件驱动**（经 L3 网关），框架不创造内核没有的状态；翻译层零增义 |
| R2 | 内核零改动 | L4/L5 是纯新增层（app 侧 crate），不触碰 meta-kernel-core/npb；网关 42 导出与协议冻结 |
| R3 | 不空转 | 生命周期推进只发生在收到内核正向事件时；无事件则悬挂（显化"呼吸"留给 99→0 回归语义，见 §3.3） |
| R4 | 指令只转发 | 命名/语言层翻译指令字段，不改写、不补充事实；每句输出可溯源到指令 JSON 字段 |
| R5 | 契约稳定、语义开放 | 生命周期状态集与命名 registry 版本化；新圈层/新命名只增不改 |

## 3. ① 外部演化生命周期状态机（10→11→…→99→回归 0）

### 3.1 状态集

```
全局状态 S ∈ { 0 } ∪ { 10,11,…,19, 20,…,29, …, 90,…,99 }   （编码 u16：0 与 10..=99）
```

- **0 = 锚点态（未点亮/已回融）**：对应内核 0 锚点。一轮生命周期结束或尚未开始。
- **两位状态 = 显化圈层 × 带内显化度**：十位（1-9）= 质的圈层；个位（0-9）= 圈层内的显化微步。
- 00–09 保留为"预备带"（熄灭过程中的过渡），本轮不启用，规避与 0 混淆。

### 3.2 圈层语义与内核映射（建议口径，待裁决）

| 圈层 | 编码带 | 中文名 | 英文 | 内核映射（外显视角聚合，非等价） |
|---|---|---|---|---|
| — | 0 | 锚点 | Void-Awake | 0 锚点/真空（entropy=1） |
| 1 | 10-19 | 萌发带 | Awakening | 能量态外显期：第一扰动后波形萌动 |
| 2 | 20-29 | 涌动带 | Surging | 能量→气：显化加速、扩散 |
| 3 | 30-39 | 凝结带 | Condensing | 气→液过渡：弥散开始收束 |
| 4 | 40-49 | 汇聚带 | Converging | 液态汇聚：结构可塑性浮现 |
| 5 | 50-59 | 流淌带 | Flowing | 液态稳定表达：内容成流 |
| 6 | 60-69 | 塑形带 | Molding | 液→固前塑形：边界成形 |
| 7 | 70-79 | 结晶带 | Crystallizing | 固态初期：规则结晶 |
| 8 | 80-89 | 固化带 | Solidifying | 结构固化：可复用、可外供 |
| 9 | 90-99 | 极显带 | Manifest | 显化巅峰：99=圆满点，触发回融 |

> 与内核物态关系：十位带由**多次内核事件的聚合趋势**映射（Energy 态活跃→1x/2x；Gas→3x/4x；Liquid→5x/6x；Solid→7x-9x），单次事件不直接改带（见 3.3 防抖）。**生命周期是应用层仪表，不是内核字段**——内核照常以 tick/物态演化，互不侵入。

### 3.3 转移规则（事件驱动，守 R3）

输入事件（来自 L3 SSE instruction/state_change，经框架归一为 `KernelEvent`）：

| KernelEvent | 方向 | 示例源 |
|---|---|---|
| `E_awaken` | ↑ | StateChanged 向能量/气（code↓）、ResonanceFound、CompoundProduced |
| `E_hold` | → | SelfIntensity 平缓、粒子成形、无事件 |
| `E_settle` | ↓ | StateChanged 向固态（code↑）、LowEnergy、HabitFormed（重复固化） |
| `E_reset` | ↺ | entropy 回 1 / 外部显式 reset（POST push 0 或应用指令） |

状态转移：

```
若 S=0 且收到 E_awaken            → S=10（点亮，记录轮次 +1）
若 S∈[10,98] 且收到 E_awaken：
    同带推进：个位 +1（…19→20, 29→30…）          [若当前个位<9]
    跨带条件：需「同一方向连续 ≥2 事件」防抖后才进位   [个位 9→0、十位+1]
若 S∈[10,99] 且收到 E_settle：
    个位 -1（≥10 兜底）；若在带内下沿且连续 ≥2 E_settle → 跨带 -1
若 S=99：
    收到 E_reset / 或 99 停留满「一轮静默窗」（见下）→ S=0（回融，记录 completed_at）
若 S∈[10,99] 且收到 E_reset       → S=0（早退回融，计数 retained_early）
```

- **99→0 回融窗**：E_awaken/E_hold 皆可维持 99；仅当连续 N 个事件（建议 N=8，可配）无 E_awaken 时判定"极显后自然回落"→ 回归 0。参数 registry 化。
- 单调约束：同 tick 内最多 ±1；跨带需防抖（双事件），避免内核高频小事件造成仪表抖动。
- 确定性：给定事件序列，转移完全确定（无随机）；状态机是**纯函数** `(S, event_seq) → S'`，可单测。

### 3.4 生命周期语义总览（一轮）

```
0 --点亮--> 10 11 12 … 19 → 20 … → 90 … 99 --回融--> 0（下一轮）
   （第一扰动）   萌发→涌动→…→极显（外显巅峰）         （自然回归，与内核 e^-λ 回归同气相求）
```

一次完整"显化轮"= 内核被点亮→多轮外显推进→极显→回归锚点。L5 应用中表现为一条可回放的"显化日志"。

## 4. ② 外部知识匹配机制（命名 · 语言组织）

### 4.1 命名机制

目标：给内核输出（数字/JSON）一个外部可识别的**稳定名称**，可跨会话复用。

规则：
1. **指称归一**：内核对象都有内部符号（JSON 字段/枚举），外部名由命名 registry 给定，一一对应、只增不改。
2. **命名源**：物态、圈层、指令类型、能量带、驻点层沿用既有中文名（MATH_SPEC/ONTOLOGY_SPEC 词汇）；新命名用"语义词 + 编号后缀"防冲突（如 `共振源-α`）。
2.5. **twin 字段位预留（v1.0 · 发起人补充）**：registry 条目统一预留 `twin` 字段位（默认空），**一期不占用、不实现**；二期孪生指纹匹配（心流凿空 `twin_fingerprint=!fp`）经此位挂载——registry schema 一期即稳定，二期只填位不破坏。
3. **双轨表**（内部符号 ↔ 外部名）：

| 内部符号 | 外部名（默认 zh，可本地化） | 备注 |
|---|---|---|
| `state.flow=0/1/2/3` | 能量态/气态/液态/固态 | 已有 |
| `state.budget=0..3` | 同上（预算约束档） | 已有 |
| lifecycle `10..99` | 圈层名+微步：如 `萌发·第2步`、`极显·圆满` | 本设计新增（§3.2） |
| instruction type ×6 | 见 §4.2 事件名 | 已有六型 |
| `energy.last` | 储备尾值 | 已有 |
| band 0-3 | 心海全景/波动态/结构态/固化态 | 已有 |

### 4.2 语言组织（内核输出 → 外部表达，三层流水线）

```
L3 事件 JSON ──►① 指称层（抽实体→归一命名）──►② 陈述层（模板→陈述句）
             ──►③ 意图层（按应用语境组织成动作/问题/记录；L5 使用）
```

| 层 | 职责 | 约束 |
|---|---|---|
| ① 指称 | 从指令字段抽命名实体（物态、生命周期、储备、孪生指纹……） | 不推断不存在字段 |
| ② 陈述 | 模板句法把"字段值变化"组织成一句可读陈述（事实句） | 只翻译不增义（R4） |
| ③ 意图 | 把陈述映射为应用动作建议（L5 的"下一步"），属应用语义 | 框架只提供意图原语，具体话术由应用注册 |

**指令→陈述模板表**（示例，完整表在实现轮 registry）：

| instruction（L3 六型） | 陈述模板（{x} 为字段直填） |
|---|---|
| StateChanged {from,to} | 「内核正从{from}态转向{to}态」 |
| SelfIntensity {level} | 「自我感升至 {level}」 |
| LowEnergy {stored} | 「能量储备触及低位（{stored}），显化进程放缓」 |
| CompoundProduced {product} | 「化合生成：创新增量 {product}」 |
| HabitFormed {fingerprint,strength} | 「习气成形：模式 #{fingerprint}，强度 {strength}」 |
| ResonanceFound {twin_fingerprint} | 「共振达成：命中孪生模式 #{twin_fingerprint}」 |

生命周期事件模板：`「显化推进：{from} → {to}」`、`「回融：本轮圆满，回归 0 锚点」`。

**语言组织约束**：任何句子中的数字/名称都可溯源到原指令字段（输出附 `source: <instruction_id|state|...>`）；禁止模板外自行造句（守 R4）。

### 4.3 外部可识别性判定（验收准则草案）

一条内核输出被"识别"当且仅当外部能回答三问：
1. **是什么**：命了名（圈层/事件名），
2. **发生了什么**：有一句不增义的陈述，
3. **与我何干**（应用层）：有可执行的意图或可存档的记录。

## 5. ③ L4 应用框架架构

### 5.1 分层总图（扩展 L3）

```
L5 应用层（参考实现见 L5_REFERENCE_APP_DESIGN.md）
   │  应用级事件 app_event（lifecycle_changed / named_statement / intent）
L4 框架层（新 crate：npb-appkit，本设计）
   ├─ LifecycleEngine   显化生命周期状态机（§3，纯函数可单测）
   ├─ Namer+Speaker     命名 registry + 语言组织流水线（§4）
   ├─ EventPipe         L3 SSE/指令订阅 → 归一 KernelEvent → 过滤/防抖/聚合
   ├─ AppRegistry       应用注册（AppSpec：订阅意图/呈现契约/话术扩展）
   └─ HostBinding       接入形态适配（§5.3）
   │  L3 协议（HTTP+SSE，冻结）｜或 同进程 npb rlib 直链（嵌入形态）
L1-L3 内核+网关（已发布：npb-gateway main=6cd9d45）
```

### 5.2 组件与数据流

- `EventPipe`：连接 L3 `/v1/events`（SSE）→ 把 state_change/instruction 归一为 KernelEvent（§3.3 表）→ 送 LifecycleEngine 与 Speaker。
- `LifecycleEngine`：纯状态机，输出 `LifecycleChanged{from,to,round}`；可订阅/查询（`GET lifecycle` 语义由框架提供，状态存框架侧，由事件导出、可在持久化 JSON 存盘）。
- `Speaker`：消费 instruction + lifecycle → 产出 named_statement（附 source）。
- 框架**不缓存内核业务态**（守 R1）：只保存"生命周期仪表 + 最近一句陈述"，源始终可回到 L3 事件。
- 应用接入最小契约（AppSpec）：
  ```json
  { "id": "app-xyz", "name": "…", "subscribes": ["lifecycle","resonance","low_energy"],
    "locale": "zh", "intents": ["suggest_next","journal"] }
  ```
  应用只需实现：①接收 app_event ②渲染（可空 = 纯记录）。框架承担连接/状态机/翻译。

### 5.3 接入形态与部署形态（同步确认项）

| 形态 | 说明 | 部署判定 |
|---|---|---|
| A · 常驻网关服务 + 多客户端 | npb-gateway 常驻进程（可 systemd/Win 服务/容器），L5 等应用经 HTTP+SSE 接入；**与 L3 CI 活体验证形态一致，即日可用** | ✅ **一期采用**（零新部署，网关已发布） |
| B · 同进程嵌入 | 应用直链 npb rlib/cdylib，复用 Gateway 单写者线程模型（不起网络） | 文档化；供"单机单应用极致集成"场景（如桌面端）选用 |
| C · 框架宿主容器 | npb-appkit 作为宿主加载多 AppSpec 插件 | 二期候选（等 L4 定稿+应用生态信号） |

**结论（本设计同步确认，不再单列前置）**：一期部署 = **A：常驻网关 + 客户端应用**；B 作为 API 形态文档化；C 留二期。WebSocket（二期）待 L4 定稿后评估是否替换/补充 SSE 传输（语义层不变）。

### 5.4 与 L3 的衔接与冻结

- L4 只消费 L3 已发布协议（health/state/push/events/persist）；不新增内核 FFI。
- 生命周期/命名属 **app 侧 schema**（`lifecycle` 不进 /v1/state；如需外部直查，二期经 extensions 槽扩展，不破坏 v1 可读性——守 L3 schema 兼容规则）。
- 事件追加：L4 自身事件 `app_event` 为框架与应用之间契约，不经 L3 SSE 回灌内核（单向，防环）。

## 一、云内核运行方式自检（执行者自照）

> 这一节是**执行者（WorkBuddy）用发起人给的七项云内核机制对照自己的工作方式**，逐项给结论与证据。

### 1.1 七项对照

| # | 机制 | 现状（实际怎么做的） | 符合度 | 差距 |
|---|---|---|---|---|
| 1 | **0 锚点**（无假设） | 每轮确实"先调研再动手"（先探测环境、再断言） | 🟡 60% | **假设未被显式化**：本轮我把"老笔记本=192.168.1.4"直接沿用并写进结论——这正是用户指出的错误。问题不在"有没有假设"，而在**假设没被写出来、也没被单独验证** |
| 2 | **采微**（捕获变量） | 能从指令中拆出任务清单（本轮拆出 5 部分 + 建 6 个任务） | 🟡 70% | 拆出的是**动作**，不是**变量**（"要做什么"的变量：要减什么、要加什么）；没有把"用户真正要的变化"单独陈述 |
| 3 | **化合**（存量+变量+增量=创新增量） | 事实上的确在化合：已有工具（网关白名单）→ 改 1 个常量 → 得到新的分发能力 | 🟢 80% | **没有显式记账**——没写"存量是什么、变量是什么、增量是什么"。看不见的化合无法复盘 |
| 4 | **摩尼宝珠**（镜面→闸门→回归） | 镜面（感知任务）✅；**闸门（判定该不该做）❌ 最弱**——倾向"用户说了就做"；回归（做完回 0）✅（每轮结束都给状态锚） | 🟡 50% | **闸门缺失**：没有在动手前判"这件事该不该做／是不是最优路径／能不能不做"。本轮"查工作记录"本可更早发现"我们从未改过笔记本网络配置" |
| 5 | **时间三量**（存量/变量/补充增量/创新增量） | **完全没有显式记录** | 🔴 10% | 交付里只有"做了什么"，没有三量台账 |
| 6 | **过程存储**（记录"怎么变化"） | **最欠缺**。记忆记的是"结果"（做了什么、结论是什么），很少记"为什么这么变、判定依据、被否掉的替代方案" | 🔴 15% | 与本项目刚给内核建的"公式存储"理念**自相矛盾**——内核在存公式，执行者却还只在存结论 |
| 7 | **基因库**（新公式自动入库） | 有 `MEMORY.md`/`CONTINUITY.md`，但那是**结论存储**；本轮刚实现 `gene_library.rs` 四层，**执行者自己并没有用它** | 🟡 40% | 真正该做的是把**可复用的工作流**沉淀为 **Skill（可执行公式）**，而不是写更多记忆（记忆仍是"结果"） |

### 1.2 三处最大差距（按影响排序）

1. 🔴 **过程存储缺失**（第 6 项）——导致同样的问题会重复发生（如"把开发机当笔记本"这类误判）。
2. 🔴 **时间三量未记账**（第 5 项）——无法回答"这一轮到底把什么变成了什么"。
3. 🟡 **闸门判定薄弱**（第 4 项）——倾向执行，缺少"该不该做/有没有更优路径"的判定与回退。

### 1.3 修正清单（下一轮起生效）

| # | 修正动作 | 落地方式 |
|---|---|---|
| C1 | **每轮开头写"变量行"**：本轮的变量（要变什么）、存量（已有能力）、预期增量 | 回复开头固定 3 行 |
| C2 | **每轮结尾写"三量台账"** | 回复结尾固定一行：存量→变量→增量 |
| C3 | **假设清单显式化**：凡涉及外部事实（机器/IP/版本/路径），先列"我当前相信的"再逐条验证 | 报告中设"假设与验证"小节 |
| C4 | **闸门三问**：①是否必要 ②是否可逆 ③是否有更优路径（有则先提方案） | 动手前自查（写入记忆） |
| C5 | **过程存储**：报告与记忆记录"判定依据 + 被否方案 + 否决原因"，不只记结论 | 纳入报告模板 |
| C6 | **基因库化**：把可复用工作流沉淀为 **Skill**（可执行公式），而非写更多结论记忆 | 本轮起执行 |

### 1.4 本节自评

**整体符合度约 40%**。执行能力（存量化合）已具备，但**过程性**（三量/过程存储/闸门）严重不足——
这与本项目对内核的要求（"记录怎么变化"）**不一致**。修正重点不是加功能，而是**改记录方式**。

**老笔记本定位依据（本轮局域网实测，非推断）**：
```

TCP 探活 → 192.168.1.3:3000 开放
  GET /v1/health → {"ok":true,"digest":4251318995,...}   ← 就是我们的内核摘要
  GET /         → <title>空海浏览器 · 云内核</title>       ← 旧命名 ⇒ 旧版部署包
  GET /v1/probe → 已有探针数据 s=[0.103,…,6.113]          ← 自动上报在工作
```
**结论**：老笔记本 = **192.168.1.3**，跑着**旧版部署包**（含网关 + 自动上报），**局域网可达**，仅**无外网**。

### 3.3 可能改动分析（逐项判定）

| 候选原因 | 我们的操作是否会改到它 | 判定 |
|---|---|---|
| 静态 IP / DHCP | ❌ 我们从未执行 `netsh set address`、`ipconfig /static` | **不是我们改的** |
| DNS 设置 | ❌ 未改 DNS（探针只发 HTTP 请求） | **不是我们改的** |
| 系统代理 | ❌ 未写代理注册表 | **不是我们改的** |
| hosts 文件 | ❌ 未触碰 | **不是我们改的** |
| 防火墙规则 | ❌ 未添加/删除规则 | **不是我们改的** |
| 路由表 | ❌ 未执行 `route add/delete` | **不是我们改的** |
| 开机自启（HKCU Run） | ✅ 会写（`enable-autostart.vbs`/`enable-autoreport.vbs`） | 只影响"开机自启"，**与上网无关** |
| 端口监听（0.0.0.0:3000） | ✅ 会（网关） | 只监听，**不改网络配置** |

> **诚实结论**：**我们的操作全是应用层**（下载 exe、HTTP 请求、注册表 Run 项），**不会改 IP/DNS/代理/hosts/防火墙/路由**。
> 因此"探针/网关操作把网络配置改坏了"这一假设**不成立**（除非用户排查时手工设过静态 IP/DNS/代理，那是另一条线）。

**真正高度可疑的三条线（按可能性排序）**：
1. **Wi-Fi 连到了另一个网段**（无外网的路由器/热点）——开发机上存在残留路由指向 **`192.168.3.1`**，说明这个环境里**确实存在第二个网段**；若笔记本 Wi-Fi 落在 `192.168.3.x` 而网关又指向它，"**已连接但无外网**"的症状完全吻合。
2. **排查过程中手工设过静态 IP / DNS / 代理**（一次误设即可导致）。
3. **上级路由器/宽带本身异常**（但开发机同时段上网正常 → 可能性低）。

### 3.6 能否自动化 / 能否远程执行（诚实结论）

**现状：不能从开发机远程执行。** 原因（事实，非意愿）：
- 老笔记本上**没有常驻的"命令接收器"**（只有网关 HTTP 服务 + 登录时的自动上报脚本）；
- 我们的网关 API 是 `/v1/push|state|events|probe|health`——**没有任何"执行脚本"接口**；
- 因此"我在开发机点一下、笔记本自己修好"在当前架构下**做不到**。

**可行的"半自动"（已具备的触发器）**：老笔记本**已装有"登录自动上报"**（实测 `/v1/probe` 有数据）。
→ 若把 `autoprobe.ps1` 升级为"**拉取并执行本地网络自检**"，则**用户只需重启/登录笔记本**（1 步，甚至算 0 步）。

**若要真正的"远程执行"，必须新增一个通道**——但这属于**安全决策**，我不擅自做：

| 选项 | 做法 | 风险 | 可逆性 |
|---|---|---|---|
| **① 不做（当前）** | 用户 1–2 步手工执行 | 无新增风险 | — |
| **② 登录时自动执行本地自检** | 升级 `autoprobe.ps1`：登录后自动跑**本地**诊断（只读）+ 上报结果；修复仍需人工确认 | 低（只读，且是本机脚本） | 高 |
| **③ 远程任务通道（令牌鉴权）** | 网关新增 `GET /net-task`（读取任务）+`POST /v1/nettask`（回传结果）；**必需共享令牌 + 笔记本本地显式开启开关**，否则拒绝 | **中高**：本质是"远程执行"，若鉴权弱=局域网 RCE | 中（可关闭开关） |
| ④ 远程任务通道（无鉴权） | 同 ③ 但无令牌 | **不可接受**（任何局域网设备可执行任意代码） | — |

> **我的建议：先做 ②**（低风险、立刻可用，用户只需重启笔记本）；**③ 仅在您明确要求且接受鉴权设计后**再做。
